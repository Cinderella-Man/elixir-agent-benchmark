Add webhooks for device events (#3117)
An organization can now send its device events to HTTP endpoints it chooses, so a customer's own systems hear about connects, health changes and firmware updates without polling the API. Each webhook sends the events of every product in the organization, or only of the products it lists. Webhooks are set up on a new Integrations page in the organization's sidebar, or through the API. ## Events - `device.connected` and `device.disconnected`. Disconnects include those found by the stale connection sweep, so a device that lost power is reported too. - `device.health_reported` and `device.metrics_reported`, carrying the readings as stored. - `device.health_status_changed`, sent when a device's status moves (healthy to warning, say), with the reasons. The previous status is read before the save, and only for products a subscribed webhook hears. - `device.firmware_update.scheduled`, `.progress` (stage changes, then at most every 15 seconds) and `.finished` with an outcome, plus `device.firmware_validated`. `.finished` is raised from `UpdateHistory.record/3`, which every outcome already passes through. - A product no webhook hears pays one ETS read per event. `Webhooks.Cache` is keyed by product, and each entry records the product's organization, so a change to any of an organization's webhooks drops all its products' entries, on every node. ## Products - A webhook sends every product's events by default, including products added later. It can list products instead (`webhook_products`). - The form and the API name products, and names are looked up only within the webhook's organization, so another organization's product is refused. - An organization can have at most 20 webhooks, which bounds how many deliveries one device event fans out into. - A webhook that is turned off notifies each product it was sending events for, since organizations have no notifications of their own. - The first commit created `product_webhooks`. The second migration renames that table rather than copying it, so an instance that ran the first keeps its webhook ids and queued deliveries, and each existing webhook is limited to the product it belonged to. ## Delivery - Deliveries are signed per the Standard Webhooks spec, so receivers can verify them with its libraries. `Signature` is tested against the spec's reference vector. - Oban jobs on a new `webhooks` queue. Device nodes insert them and web nodes deliver them. - Retries (6 attempts over about 2.5 hours) are snoozes rather than errors. The Sentry Oban integration reports every `{:error, _}`, and one broken receiver would flood it. Crashes in our code still raise. - After a failure, a webhook's deliveries skip the request for 30 seconds, so an unreachable endpoint can't fill the shared queue. A webhook failing for 24 hours, or answering 410, is turned off. ## Server-side request forgery - Webhooks only reach public addresses unless `WEBHOOKS_ALLOW_PRIVATE_DESTINATIONS` is set (on in dev). A literal private address is refused on save. A host name is resolved at delivery and refused if any address it resolves to is private. - The request goes to the address that was checked. `Delivery.Adapter` opens a one-shot Mint connection to it, keeping the host name for TLS, so DNS can't answer the check with one address and the connection with another. Req's `connect_options: [hostname: ...]` could pin the address, but it starts a Finch instance named by a new atom for each distinct option set, which would leak one per host name. - Redirects are not followed, since the address a redirect points at was never checked. A 3xx counts as a failed delivery. ## Access - Managing webhooks needs the organization `manage` role, through new `webhook:create`, `webhook:update` and `webhook:delete` permissions. In the API, reads need it too. - View-only members see each webhook's host, products and events, but not its URL or secret, because some receivers keep credentials in the URL. Audit log entries are recorded against the organization and name the host for the same reason. - The API returns the signing secret only from create and regenerate. `docs/webhooks.md` is written for receivers: payloads, headers, verification, retries and the API. `WEBHOOKS_ALLOW_PRIVATE_DESTINATIONS` is in `docs/runtime_configuration.md`. 🤖 Generated with [Claude Code](https://claude.com/claude-code) --------- Co-authored-by: Claude Opus 5.5 <noreply@anthropic.com>
