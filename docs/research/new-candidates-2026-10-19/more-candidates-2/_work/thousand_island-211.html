What this adds

A new top-level server option, handshake_timeout, bounding how long a freshly accepted connection may take to complete its transport handshake (TLS negotiation, in practice). It defaults to 5000 ms; :infinity disables the bound. When the timeout elapses, the connection tears down through the existing handshake-error path: the socket is closed, the num_connections slot is reclaimed, and the handler sees c:handle_error/3 with a reason of :timeout.

Why it matters

Today the SSL transport performs its handshake with :ssl.handshake(socket), which per the OTP docs is equivalent to a call with an infinite timeout. read_timeout only begins counting after the handshake returns, and nothing else bounds the window. The consequence: a client that opens a TCP connection to a TLS listener and then goes quiet, or dribbles handshake bytes slowly, holds a connection process, a file descriptor, and one slot of num_connections indefinitely. A modest number of such sockets, malicious or just broken, quietly eats capacity; with the default capacity math (100 acceptors x 16,384 connections) the file descriptor limit is usually what actually gives out first.

The OTP ssl documentation calls the risk out directly: "Not setting the timeout makes the server more vulnerable to Denial of Service (DoS) attacks." Ranch has bounded this window since 1.6 with a handshake_timeout option defaulting to 5000 ms (confirmed at source: maps:get(handshake_timeout, TransOpts, 5000) in ranch_conns_sup), so this is straight competitive parity as well as hardening. It appears there's some history on this subject of servers meet exactly this kind of traffic: the :econnaborted handling added to the acceptor in PR #72 was motivated by "SSL weakness probing or incomplete TCP handshakes" observed in the wild.

Standards and prior art

RFC 8446 does not mandate a server-side handshake timer, but bounding half-open negotiations is standard TLS server hardening, and every mainstream implementation does it: Ranch (handshake_timeout, 5000 ms), nginx (ssl_handshake_timeout), HAProxy (timeout client applies during the handshake). The mechanism here uses only the documented :ssl.handshake/2 timeout argument, available since OTP 21.

Design rationale

The plumbing mirrors how read_timeout already flows through the codebase: an option on ThousandIsland, a field on ServerConfig, copied into HandlerConfig (the struct acceptors precompute once), carried on the Socket, and consumed at the single handshake call site in Socket.handshake/1.

The decision worth defending in review is how the timeout reaches transports. ThousandIsland.Transport.handshake/1 takes only a socket, and custom transports are a documented extension point of this library (the "When Handler Isn't Enough" escape hatch; issues #141 and #144 both involve people building them), so changing that callback's arity would break them at runtime. Instead, handshake/2 (socket, timeout) is added as an optional callback alongside the existing handshake/1: Socket.handshake/1 prefers handshake/2 when the transport exports it and falls back to handshake/1 otherwise, via a one-line function_exported?/3 check. Both bundled transports implement it (TCP ignores the timeout, since it has no handshake; SSL passes it to :ssl.handshake/2), and a dedicated compatibility test exercises a transport that implements only handshake/1 to lock the fallback in. This is the same optional-callback pattern OTP itself uses to evolve behaviours.

On the default: 5000 ms matches Ranch and the OTP guidance, and makes servers safe out of the box. It is a deliberate behavior change for TLS servers that relied on unbounded handshakes, which is why the docs state it plainly and the suggested PR text below proposes a changelog note in the same spirit as the 1.5.0 timeout-separation note. If the maintainer prefers introducing the option with zero behavior change, flipping the default to :infinity is a one-line change and the rest of the PR stands as is.

Performance

Nothing on the per-byte path. Per connection, the additions are one struct field copy and one function_exported?/3 check (a BIF, nanoseconds) before the handshake call. The timeout itself is managed inside OTP's ssl app, which already runs a timer-capable state machine per handshake. TCP connections are completely unaffected.

Tests

Four tests in a new test/thousand_island/handshake_timeout_test.exs:

  1. Configuration: handshake_timeout defaults to 5_000 and accepts :infinity.
  2. Stalled handshake: a client connects to a TLS listener at the TCP level and never begins a handshake; with handshake_timeout: 250 the handler's handle_error/3 receives :timeout, connection_pids/1 returns empty (the slot is reclaimed), and the client observes the close.
  3. Happy path: a well-behaved TLS client handshakes and echoes normally under the default timeout, with no option passed.
  4. Compatibility: a transport defined in the test file that implements only handshake/1 (delegating everything else to the TCP transport) serves a full echo round trip with a finite handshake_timeout configured, proving third-party transports keep working untouched.

## Suggested PR description

Title: `Add a handshake_timeout server option (default 5000 ms)`

> A client that connects to a TLS listener and then goes quiet (or dribbles handshake bytes) currently holds its connection process forever: `:ssl.handshake/1` runs with an infinite timeout, and `read_timeout` only starts counting after the handshake completes. Each such socket pins a process, an fd, and a `num_connections` slot. The OTP docs call this out directly ("Not setting the timeout makes the server more vulnerable to Denial of Service (DoS) attacks"), and ranch has bounded it with a 5 second default since 1.6.
>
> This adds a `handshake_timeout` option, plumbed the same way `read_timeout` is (ServerConfig -> HandlerConfig -> Socket) and applied at the existing single handshake call site. On timeout the connection tears down through the existing handshake-error path and the handler sees `handle_error/3` with `:timeout`.
>
> To keep third-party transports working, `handshake/2` lands as an optional callback alongside the existing `handshake/1`: `Socket.handshake/1` prefers `handshake/2` when a transport exports it and falls back to `handshake/1` otherwise (one `function_exported?/3` check per connection; nothing on the data path). Both bundled transports implement it, TCP ignoring the timeout. A test exercises a transport that implements only `handshake/1` to lock the compatibility in.
>
> The default is 5000 ms to match ranch and the OTP guidance, with `:infinity` restoring the previous behaviour. That is a deliberate behavior change for TLS servers that relied on unbounded handshakes, so it likely deserves a changelog note in the same spirit as the 1.5.0 timeout-separation note; happy to flip the default to `:infinity` instead if you'd rather introduce this without any behavior change.
>
> Tests cover the stalled-client teardown (error callback, slot reclaimed, client sees close), the happy path under the default, the only-handshake/1 transport fallback, and config defaults.
