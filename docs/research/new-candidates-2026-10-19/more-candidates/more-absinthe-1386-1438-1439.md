## Authentic work

GraphQL's September 2025 spec adds `@oneOf` input objects: exactly one field set and non-null, all others omitted. Absinthe #1386 implements the directive end-to-end (notation, schema validation, document validation, pipeline registration, SDL/introspection name). Two same-day follow-ups complete the product:

1. **#1438** — `__Type.isOneOf` is missing from introspection. Clients cannot discover oneOf input types. Adds the introspection field, the `FullType` fragment entry, and coverage.
2. **#1439** — document validation only walked top-level arguments, so a oneOf input object **inside a list** escaped the "exactly one non-null field" rule. Rebinds validation onto `%Absinthe.Blueprint.Input.Object{}` so nested/list occurrences are checked.

Per LINEAGE-MERGE-POLICY rule "PR A ships a rule; PR B fixes that rule's obvious hole → one case, ticket describes B's outcome": the holes (#1438, #1439) are obvious from the spec contract a careful solver would implement. Do **not** score three near-duplicate cases.

## Cross-component behavior to verify

- Schema phase: `@oneOf` rejected on non-input types, on single-field inputs, and when any field is non-null.
- Document phase: input object with `@oneOf` must have exactly one non-null field — for direct arguments **and** for objects nested in lists (`list_of(:valid_input)`).
- Pipeline runs both phases (schema compile-time and document execution-time).
- Introspection: `__Type.isOneOf` is `true` for marked input objects, `false`/`null` otherwise; present in the standard `FullType` fragment.
- Directive is named `one_of` in Elixir notation and `oneOf` in GraphQL/introspection output.

## Draft ticket (short maintenance report)

> Support the GraphQL September 2025 `@oneOf` input object directive. An input object marked `@oneOf` may have more than one field in its definition, but every field must be nullable, and at execution a client must set exactly one field to a non-null value. Reject invalid schema uses and invalid documents, including oneOf objects that appear inside list inputs. Introspection must expose whether an input type is oneOf so clients can discover it.

Do **not** put internal phase module names in the solver ticket. Public surface to freeze if graded: directive name `one_of` / `oneOf`, and introspection field `isOneOf` (product API from upstream).

## Acceptance design (proposed, unexecuted)

- Schema: `@oneOf` on a 1-field input → error; `@oneOf` with a non-null field → error; valid multi-nullable-field input → compiles.
- Document: zero or 2+ non-null fields on a oneOf object → the spec error message; exactly one non-null → runs.
- Document (list): `arg :inputs, list_of(:valid_input)` with an inline list entry that sets two fields → **same** error (this is the #1439 hole).
- Introspection: `__type(name: ...){ isOneOf }` is `true` for a marked type and `false` for a normal input object.

## Plausible incomplete (proposed)

Ship #1386 semantics only: validation that never fires for list elements, and no `isOneOf` on introspection. Compiles and passes direct-argument tests; named list and introspection assertions fail. This is exactly the natural intermediate control.

## Integrity control (proposed)

Acceptance must not pass if `isOneOf` is always `true`/always `false`, if list-nested oneOf objects skip validation, or if schema validation accepts non-null fields under `@oneOf`.
