## 1. ExDoc #2270: XML-safe EPUB metadata and titles

**Why it adds variety.** This is an artifact-generation task: a source project, metadata and Markdown extras become an EPUB archive containing several XML documents. A parser can verify the result independently of string formatting. It adds templating, serialization and packaging coverage without a browser or remote service. [PR and complete diff](https://github.com/elixir-lang/ex_doc/pull/2270/files).

**Draft brief:** “EPUB generation produces invalid XML when project metadata or an extra page's title contains characters such as `&`. Preserve the literal metadata and titles while generating well-formed package, cover and page documents.” Require exact semantic values after XML decoding, not a particular entity spelling or helper function.

The accepted patch changes `content_template.eex`, `head_template.eex` and `title_template.eex`, covering package metadata/attributes, page headers and cover content. The added test generates a real EPUB, unzips it and passes selected documents to `:xmerl_scan`; it checks a project title, author and extra heading containing `&`. It does not cover every newly escaped field. [Pinned implementation/test change](https://github.com/elixir-lang/ex_doc/commit/9d4d337a43dca7f7f481b7686977e4cc6c5ef271).

Proposed checks should parse all relevant generated documents and inspect decoded project/version/author/page-title values, retaining ordinary ASCII and Unicode text. Use realistic language tags rather than making an invalid language code a hidden requirement. Include a harmless value containing literal entity-looking text to distinguish correct escaping from double interpretation. A partial solution escaping only the package metadata should still fail a cover/header assertion; deleting the title or dropping the extra page must not pass. Valid existing navigation and ordinary documents remain preservation checks. These proposals have not run.

**Do not claim complete EPUB conformance.** XML well-formedness is narrower than every EPUB schema, identifier and link-validity rule. The patch is evidence for the stated escaping repair, not a certificate that every possible project name yields a specification-valid book. Use independent XML parsing and decoded content as the immediate boundary, and investigate any broader desired contract separately.

The earlier [#2269](https://github.com/elixir-lang/ex_doc/pull/2269/files) repairs configured filenames in manifest/navigation IDs and hrefs, a related but different source of XML corruption. It already exists in #2270's baseline. Do not count the two as independent defect-family coverage or require reimplementation of already-correct filename behavior. #2269's explicit AI-assistance disclosure is provenance metadata, not difficulty or solvability evidence.

**Environment.** The [starting Mix project](https://github.com/elixir-lang/ex_doc/blob/4b4e51aa4edf35b5bf113e6a839e93008c54e937/mix.exs) requires Elixir `~> 1.15`, adds `:edoc`/`:xmerl` for tests and compiles test support. The [test helper](https://github.com/elixir-lang/ex_doc/blob/4b4e51aa4edf35b5bf113e6a839e93008c54e937/test/test_helper.exs) compiles local module fixtures and conditionally excludes OTP documentation features. Pin an actual Elixir/OTP pair and preserve required checks through those exclusions. The [historical CI](https://github.com/elixir-lang/ex_doc/blob/4b4e51aa4edf35b5bf113e6a839e93008c54e937/.github/workflows/ci.yml) includes Elixir 1.18/OTP 27, among other pairs. A [lockfile](https://github.com/elixir-lang/ex_doc/blob/4b4e51aa4edf35b5bf113e6a839e93008c54e937/mix.lock) is present; `lazy_html` is a native test dependency whose availability still needs preparation.

The source contains [prebuilt formatter assets](https://github.com/elixir-lang/ex_doc/tree/4b4e51aa4edf35b5bf113e6a839e93008c54e937/formatters). The proposed repair changes EEx templates, so rebuilding JavaScript is not itself an acceptance requirement. Verify that the retained assets suffice in the isolated fixture rather than blindly running the general `build` alias, which also runs npm and the project's own docs workflow. License: [Apache-2.0](https://github.com/elixir-lang/ex_doc/blob/4b4e51aa4edf35b5bf113e6a839e93008c54e937/LICENSE).

## 2. Credo #1258: diagnose misnamed test files

**Why it adds variety.** This is a developer-tool feature using source AST and filenames, rather than executing the submitted sample programs. The upstream request describes a `_text.exs` typo that made a test disappear from the ordinary suite. The accepted implementation adds `Credo.Check.Warning.WrongTestFileName`. [Request and review](https://github.com/rrrene/credo/pull/1258), [complete diff](https://github.com/rrrene/credo/pull/1258/files).

**Draft brief:** “Add `Credo.Check.Warning.WrongTestFileName` for misnamed test files. For the check's configured source files, inspect literal module names in `use` expressions and warn on `ExUnit.Case` and conventionally named helpers whose final module component ends in `Case`, unless the filename ends in `_test.exs` or `_case.ex`. Report the triggering use and its location; preserve unrelated `use` expressions.” The public check name is part of the requested interface. The naming convention is a deliberate heuristic. It does not prove whether an arbitrary module is really an ExUnit case, resolve aliases or reproduce all Mix test-discovery configuration.

The reference has one new implementation file and one test file. Tests cover several case-helper names, options, correct suffixes and unrelated modules. Add the actual `_text.exs` and `test_my_module.exs` examples plus the case-helper exemption; verify trigger/line identity without requiring exact explanatory prose. An incomplete implementation that recognizes only `ExUnit.Case` should fail helper-module examples while passing ordinary ones. A broad implementation that flags every `use` must fail positive preservation. [Pinned tests](https://github.com/rrrene/credo/blob/cfed224855cbee5a49dcf8f194fe4ab29707410b/test/credo/check/warning/wrong_test_file_name_test.exs).

Invoke the requested check explicitly in the fixture. The PR does not by itself establish that every default Credo invocation enables it. New-module checks must assert availability within a named test body so the unchanged source fails behaviorally rather than through global test compilation. Parsed snippets should not execute external commands or application modules.

**Environment.** The [accepted commit](https://github.com/rrrene/credo/commit/cfed224855cbee5a49dcf8f194fe4ab29707410b) is a two-parent merge; the first parent is the recorded starting state, not the PR API's later base SHA. Its delta adds exactly the two files. The [starting Mix project](https://github.com/rrrene/credo/blob/b991faf933c6edce56124fbb2bf1ee9e33893fac/mix.exs) declares Elixir `>= 1.13.0`, a [lockfile](https://github.com/rrrene/credo/blob/b991faf933c6edce56124fbb2bf1ee9e33893fac/mix.lock) exists, and the [helper](https://github.com/rrrene/credo/blob/b991faf933c6edce56124fbb2bf1ee9e33893fac/test/test_helper.exs) excludes version-tagged, housekeeping and unimplemented checks. The test alias also filters slow tests. A specific modern pairing and required-check inclusion remain to qualify; the AST-only task needs no external service. [MIT license](https://github.com/rrrene/credo/blob/b991faf933c6edce56124fbb2bf1ee9e33893fac/LICENSE).

## 3. Cachex #407 + #411: preserve caller context across processes

**Why it adds variety.** User callbacks execute in cache workers rather than the initiating process. Libraries that find caller-owned stubs through `:"$callers"` then lose the originating context. The [feature discussion](https://github.com/whitfin/cachex/pull/407) and [issue #406](https://github.com/whitfin/cachex/issues/406) establish that user problem; the maintainer explicitly links [follow-up #411](https://github.com/whitfin/cachex/pull/411). That follow-up fixes scheduled warming, covers another queued execution path and preserves older Elixir compatibility. It is not merely test cleanup despite its title.

**Draft brief:** “Propagate the initiating caller context into fetch fallbacks, queued update/transaction callbacks, hooks and explicitly triggered warmers, so caller-owned stubs remain discoverable. Preserve cache results, locking, same-key fallback coalescing and callback behavior, and keep recurring warmers working after their first execution. Separate callback executions must receive their own initiating context.” The visible contract must settle any required exact chain order. Caller discoverability and isolation do not inherently require every internal worker PID or a particular private helper/macro.

Seven implementation paths participate: `actions/warm.ex` bridges explicit warming; `hook.ex` and `services/informant.ex` transfer hook context; `services/courier.ex` forwards it into fallback workers; `services/locksmith/queue.ex` handles queued execution/transactions; `warmer.ex` handles explicit and scheduled callbacks; `spec.ex` supplies shared context access. This is a coherent larger exception, not seven unrelated fixes. The feature adds four test paths and documentation. The correction updates those tests and a shared hook helper. [Feature diff](https://github.com/whitfin/cachex/pull/407/files), [correction diff](https://github.com/whitfin/cachex/pull/411/files).

Proposed checks should create two independent initiating processes, register distinct caller-local sentinel values, and exercise each public callback route with explicit message acknowledgements. For isolation, use sequential calls or different uncached keys so each callback is actually supposed to execute. Assert the correct initiating chain and unchanged cache updates/return values; reusing a cache must not leak the previous caller. Separately preserve concurrent same-key fetch coalescing: waiting callers share the existing fallback worker and its initiating context, rather than each executing a new fallback. Exercise a recurring warmer's next tick using a reviewed deterministic timer/message seam, without measuring how quickly it fires. A fallback-only implementation is a natural partial control; the original #407 feature is another, because it changes the warmer message shape but leaves rescheduling on the old shape. Do not grade private message tuples as requirements; prove their observable lifecycle consequence. All checks remain proposals.

**Source reconstruction trap.** #411 was rebased into ten accepted commits. Its API `merge_commit_sha`, `15fe44032e90c2da82ef8a445d7d7fd7974da84a`, is only the last correction, touching one file. Its immediate parent is not the pre-#411 baseline. The accepted correction range starts after `df6ae71d975fec633c2fd64f6526ae3afe9f4886` and runs through `15fe440…`; the PR's original branch commit SHAs differ from accepted history. [Accepted range](https://github.com/whitfin/cachex/compare/df6ae71d975fec633c2fd64f6526ae3afe9f4886...15fe44032e90c2da82ef8a445d7d7fd7974da84a).

The complete [pre-feature-to-fixed interval](https://github.com/whitfin/cachex/compare/7f175962e746869d12088c235e39e63f37033334...15fe44032e90c2da82ef8a445d7d7fd7974da84a) contains **13 commits and 17 changed paths**, including intervening repository-wide formatting configuration/test edits and removal of the new testing documentation. Select the coherent source intentionally; do not import every chronological edit or use only the last one-file commit. A selected composite would need the source-reconstruction support discussed in the [previous pass](expanded-case-research-2026-10-18.md#the-current-source-verifier-what-already-works-and-what-needs-support). This pass did not construct or execute that composite.

**Environment.** The [starting Mix project](https://github.com/whitfin/cachex/blob/7f175962e746869d12088c235e39e63f37033334/mix.exs) declares Elixir `~> 1.7`, with ETS/process-related dependencies and `local_cluster` for tests. There is **no committed `mix.lock`** at the inspected base; dependency resolution must be pinned and reviewed as preparation evidence. The test alias starts EPMD and the [helper](https://github.com/whitfin/cachex/blob/7f175962e746869d12088c235e39e63f37033334/test/test_helper.exs) loads shared test utilities. The proposed case is single-node caller propagation, but the selected test files/support still need auditing for incidental cluster startup and resource counts. [Historical CI](https://github.com/whitfin/cachex/blob/7f175962e746869d12088c235e39e63f37033334/.github/workflows/ci.yml) includes a separate speed job; it is outside this functional task and must not be run here. No universal compatibility claim follows from testing only a modern Elixir version. [MIT license](https://github.com/whitfin/cachex/blob/7f175962e746869d12088c235e39e63f37033334/LICENSE).

## 4. Swoosh #665: custom inline attachment IDs, with a reference hold

**Why it adds variety.** The [request #658](https://github.com/swoosh/swoosh/issues/658) needs caller-chosen content IDs because messages can contain duplicate filenames or HTML whose IDs are already determined. The accepted [#665](https://github.com/swoosh/swoosh/pull/665/files) adds `cid` to attachment construction and uses it in OhMySMTP and Postmark payloads. This coordinates one common value with two provider contracts. `lib/swoosh/email.ex` only updates doctest struct output; the substantive implementation count is **three**, not four. Three test files change.

**Draft outcome once corrected:** support explicit IDs for inline attachments, preserve filename-based defaults when omitted, omit inline IDs for ordinary attachments, and carry the chosen ID through both provider payloads without changing attachment bytes, names or content types. Check both file-backed and `{:data, binary}` construction, mixed inline/ordinary attachments and duplicate filenames with distinct explicit IDs. Use different payloads/IDs so one hard-coded value cannot pass. A partial implementation that updates construction and only one adapter should fail the other adapter's request assertion.

**Concrete source concern.** The [starting constructor](https://github.com/swoosh/swoosh/blob/7f5d55ae3407430fb12940eb57a1458c20894499/lib/swoosh/attachment.ex) has separate data and path clauses. #665 only computes the default `cid` in the path clause. The data clause still constructs the struct directly, leaving `cid: nil` if the caller supplies `filename` but no explicit ID. Both changed adapters now use `attachment.cid` where they previously used `attachment.filename`. Thus an existing in-memory inline attachment with a filename is predicted to lose its default content ID. This is source-level reasoning, not an executed regression. The originating request itself mentions in-memory data, so simply excluding that constructor would weaken the intended capability.

Hold the reference until a named preservation test and an attributable correction resolve that path. The inspected later [#1155](https://github.com/swoosh/swoosh/pull/1155) fixes a different Mailpit adapter field-name mistake and adjusts a Mua test expectation; it does not change attachment construction and is not evidence that #665's constructor behavior was repaired. No correcting lineage was established in this bounded search. Do not treat [#669](https://github.com/swoosh/swoosh/issues/669)'s SMTP download-filename report as proof of this different CID defect either.

**Offline feasibility.** The historical [Postmark tests](https://github.com/swoosh/swoosh/blob/7f5d55ae3407430fb12940eb57a1458c20894499/test/swoosh/adapters/postmark_test.exs) and [OhMySMTP tests](https://github.com/swoosh/swoosh/blob/7f5d55ae3407430fb12940eb57a1458c20894499/test/swoosh/adapters/oh_my_smtp_test.exs) use Bypass loopback endpoints and fake API keys. A case can inspect real serialized request bodies without sending email or contacting either provider. The [helper](https://github.com/swoosh/swoosh/blob/7f5d55ae3407430fb12940eb57a1458c20894499/test/test_helper.exs) excludes integration-tagged tests and starts Bypass; preserve that local boundary. The [Mix project](https://github.com/swoosh/swoosh/blob/7f5d55ae3407430fb12940eb57a1458c20894499/mix.exs) requires Elixir `~> 1.10`, with a [lockfile](https://github.com/swoosh/swoosh/blob/7f5d55ae3407430fb12940eb57a1458c20894499/mix.lock). The [CI](https://github.com/swoosh/swoosh/blob/7f5d55ae3407430fb12940eb57a1458c20894499/.github/workflows/elixir.yml) includes Elixir 1.13/OTP 24. Historical HTTP dependencies still need offline preparation. [MIT license](https://github.com/swoosh/swoosh/blob/7f5d55ae3407430fb12940eb57a1458c20894499/LICENSE.txt).
