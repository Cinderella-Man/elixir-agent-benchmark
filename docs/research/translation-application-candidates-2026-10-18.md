# Accent application candidates — 2026-10-18

Accent is an actual application for translators and their colleagues: users maintain translations, discuss them, manage collaborators and export localized files. Its first-party README describes a self-hostable web UI, history, comments, GraphQL API and CLI; the historical source is BSD-3-Clause. This is a product-purpose screen, not a security audit. The inspected purpose is translation collaboration, with optional operational error/APM reporting documented separately; no surveillance product was selected. Historical fixtures should have no third-party reporting credentials and operate offline. [Project README](https://github.com/mirego/accent#readme), [historical license](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/LICENSE.md), [2023 reporting configuration](https://github.com/mirego/accent/blob/98eb7f93dca39713e4c8557882c63437d36d748f/config/runtime.exs).

This note follows the repository's [selection guidance](../pr-selection-guidelines.md), [admission requirements](../case-admission.md), and [rejection register](../../cases_rejected/README.md). No Accent identity appeared in the existing research/rejection records inspected. Evidence below is source inspection only: no application code, builds, tests, model attempts or performance measurements ran. All candidates remain outside the inventory. Proposed checks and partial controls are curator designs, not executed evidence.

## 1. Version requirements across export and synchronization — #183

**Source and pair.** The authentic request was to obtain compatible translation versions without updating every client's exact tag. The merged PR explicitly introduces `Version.Requirement` fallback when there is no exact tag. Accepted commit `e11088f6ec0b58fdb8dc0d0948ba167ed5388dc2`, verified first parent `9cdd5626da8cb71e4ef2ab45afc8b73632470cfe`. [Issue #171](https://github.com/mirego/accent/issues/171), [PR](https://github.com/mirego/accent/pull/183), [accepted commit](https://github.com/mirego/accent/commit/e11088f6ec0b58fdb8dc0d0948ba167ed5388dc2).

**Coordinated work.** `lib/accent/schemas/version.ex` parses stored tags, `lib/accent/scopes/version.ex` prefers literal matches and otherwise selects the highest matching semantic version, and `lib/web/plugs/movement_context_parser.ex` applies the project scope before this now-executing lookup. The last change matters: a query helper that used to merely add a predicate now reads candidates, so applying project scoping afterward can select another project's tag and subsequently return no version. Export already scopes before lookup; sync/merge use the movement parser. The upstream regression file covers exact tags, a literal tag that looks like a requirement, `v` prefixes, maximum compatible version and malformed stored tags, but not the mixed-project request path. [Full PR diff](https://github.com/mirego/accent/pull/183/files), [export controller](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/lib/web/controllers/export_controller.ex), [routes](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/lib/web/router.ex).

**Proposed visible brief.** “Allow file export and sync/merge requests to select a project's translation version with a semantic version requirement such as `~> 1.1`. Prefer an exact literal tag when present; otherwise select the highest compatible version in that project, accepting stored tags with a leading `v` and ignoring non-version tags. Preserve the existing outcomes for unmatched requests and requests without a version.” This is a clarified feature brief, not a disguised one-sentence repair. Avoid silently requiring additional prerelease or equal-precedence tie policies: either preserve the starting standard-library behavior or clarify any scored policy.

**Oracle.** Seed project A with `v1.1.2` and `1.1.4`, and project B with `1.1.9`; export A and assert A's `1.1.4` contents. Sync/merge A with the same requirement and assert the resulting persisted translations/operations target A's selected version. Separately use a literal tag `~> 1.1` and verify literal priority. Include malformed tags, no matching version, omitted version and an unrelated project's unchanged translations. Use actual authenticated local controller requests with PostgreSQL, not only the query helper. Preserve each route's existing unmatched-result behavior; do not impose one status on all routes.

**Plausible incomplete control.** Apply semantic lookup but retain the original movement-parser order. It compiles and can pass export/helper tests while the cross-project sync/merge witness fails. A second useful control returns the first compatible version instead of the highest. Named assertions should demonstrate the missing behavior rather than setup failure.

**Runtime.** Historical CI uses Elixir `1.9.x`, OTP `22.3.3`, PostgreSQL 10 and Node `10.14.x`; Mix requires Elixir `~> 1.9`. Dependencies include a pinned Git `fast_yaml` revision requiring native YAML support and an older Git Ueberauth dependency. `mix test` creates/migrates the database; the test configuration uses SQL Sandbox, dummy authentication, a test mailer and mocked external hook/spelling boundaries. CI additionally builds the Ember webapp before its broad suite. A focused controller fixture may not need the browser bundle, but that has not been demonstrated. Pin exact available toolchain/dependency artifacts rather than assume current OTP compatibility. [Historical CI](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/.github/workflows/ci.yml), [Mix project](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/mix.exs), [lock](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/mix.lock), [test config](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/config/test.exs).

**Follow-up screen and next action.** Path histories were inspected for the version scope and movement parser; they did not identify a focused correction to this requirement-selection behavior. This is a bounded screen, not proof that all edge cases are correct. Draft the request-level fixture first, then challenge exact-tag precedence and project isolation before model work. [Scope history](https://github.com/mirego/accent/commits/master/lib/accent/scopes/version.ex), [parser history](https://github.com/mirego/accent/commits/master/lib/web/plugs/movement_context_parser.ex).

## 2. Edit your own discussion comments — #236

**Source and pair.** Users asked to edit/delete comments; this PR implements editing from both the translation conversation and project conversation views. Accepted `09e4301aea447998d76050f95719730a79832f38`, first parent `b12c05525e317f17eee5bf5331d46db6a78651a9`. Comment deletion already exists in the starting tree through [#224](https://github.com/mirego/accent/pull/224), so do not describe deletion as newly reconstructed here. [Issue #211](https://github.com/mirego/accent/issues/211), [PR #236](https://github.com/mirego/accent/pull/236), [accepted commit](https://github.com/mirego/accent/commit/09e4301aea447998d76050f95719730a79832f38).

**Workflow and contract.** Four backend implementation paths add update permission presentation, a text changeset, GraphQL mutation and persistence resolver. The Ember change threads the action through both views, pre-fills an edit form, submits a GraphQL operation and refreshes the appropriate conversation query. The diff has 26 paths: 21 behavioral code/template/style paths, three TypeScript interface-only additions, one resolver-test file and one CI-file update. This is coherent larger application work, not a 4-file backend feature with the UI omitted. [Diff](https://github.com/mirego/accent/pull/236/files).

**Proposed visible brief.** “Let users edit their own comments from both a translation's conversation and the project's conversation list. Start with the existing text; allow cancellation without saving; after a successful edit display the saved text and preserve it after reload. Reject empty text and prevent another user from editing a comment through the API.” Author-only behavior is stated by the PR and enforced by the starting comment authorization helper/Canada implementation. Do not silently add a new rule about former project members: the historical policy compares the comment author to the current user, and membership changes need separate product review. [Authorization helper](https://github.com/mirego/accent/blob/b12c05525e317f17eee5bf5331d46db6a78651a9/lib/graphql/helpers/authorization.ex), [author predicate](https://github.com/mirego/accent/blob/b12c05525e317f17eee5bf5331d46db6a78651a9/lib/accent/auth/canada_implementations.ex).

**Oracle and incomplete control.** A real local browser should exercise both views, cancel, save and reload, paired with direct authenticated GraphQL requests for empty text and another author's comment. Preserve creation/deletion and unrelated comments. The upstream new test calls `Resolver.update/3` directly and only proves persistence of valid text; it does not prove the authorization wrapper or either UI path. A plausible partial implementation updates the backend and translation view but leaves the project list disconnected; the project-view assertion should fail while the other assertions pass. A UI-only ownership check must fail the unauthorized API assertion. API naming should only be fixed in the visible brief if the benchmark actually scores that public GraphQL shape.

**Execution hold.** Historical Mix requires Elixir `~> 1.11` and compiles Gleam in test mode. The parent CI lists OTP `23.1.1`, Elixir `1.11.x`, Node `10.14.x`, PostgreSQL 10 and Gleam `0.11.2`; the PR changes CI to Gleam `0.13.2`, while the parent's Docker build already uses `0.13.2`. Resolve and record this discrepancy, retaining the upstream CI edit in source reconstruction. Ember source is pinned `3.23.1`, CLI `3.22.0`. The existing Node adapter does not automatically run an Ember acceptance suite, and the old Alpine release image cannot be assumed to satisfy the runner's Ubuntu browser recipe. This is a reserve until a pinned local build/browser fixture is proven. [Historical Mix](https://github.com/mirego/accent/blob/b12c05525e317f17eee5bf5331d46db6a78651a9/mix.exs), [CI](https://github.com/mirego/accent/blob/b12c05525e317f17eee5bf5331d46db6a78651a9/.github/workflows/ci.yml), [Dockerfile](https://github.com/mirego/accent/blob/b12c05525e317f17eee5bf5331d46db6a78651a9/Dockerfile), [webapp dependencies](https://github.com/mirego/accent/blob/b12c05525e317f17eee5bf5331d46db6a78651a9/webapp/package.json).

## 3. Android plural export — #378

**Source and pair.** An actual user observed that database translations marked plural were exported as separate ordinary strings. The reference carries `plural`, `placeholders` and `locked` from persisted translations into formatter entries. Accepted `0805e6b3855f1e2e3c316fecc3e0929f12c5187f`, first parent `98eb7f93dca39713e4c8557882c63437d36d748f`. One implementation path, `lib/accent/translations/translations_renderer.ex`, plus an export-controller regression. [Issue #303](https://github.com/mirego/accent/issues/303), [PR and diff](https://github.com/mirego/accent/pull/378/files), [accepted commit](https://github.com/mirego/accent/commit/0805e6b3855f1e2e3c316fecc3e0929f12c5187f).

**Draft contract and oracle.** “Export Android plural translations as plural resources with the correct quantity variants, preserving ordinary strings and their values.” Test the authenticated export route against persisted plural and ordinary translations, checking parsed XML structure and values rather than incidental whitespace. The upstream test covers two variants of one `days` group. Do not silently add Gettext placeholder/locking requirements merely because the reference also forwards those fields; a broader metadata contract needs an explicit brief and separate witnesses.

**Reference concern: hold.** Static inspection of the unchanged Android serializer shows every consecutive plural entry appended to one `current_plural` accumulator. It does not flush when the plural resource key changes, and `add_plural_item/3` sets its key from `current_array_key || key`, rather than preserving a distinct group boundary. Adjacent `days.one`, `days.other`, `cats.one`, `cats.other` can therefore be combined into a single resource. This is a source-derived hypothesis, not an executed failure. A reference challenge must test multiple groups before this becomes an admitted general plural-export case; do not quietly restrict fixtures to the single upstream example to conceal the issue. [Serializer at the accepted revision](https://github.com/mirego/accent/blob/0805e6b3855f1e2e3c316fecc3e0929f12c5187f/lib/langue/formatter/android/serializer.ex).

The next renderer change includes a Gettext plural-order regression alongside unrelated lint/UI work; it is not a clean Android group correction and should not be indiscriminately attached. [Later mixed commit](https://github.com/mirego/accent/commit/ca99b09e546ced3394ed8d1ff7074c21c6c0fa71). No plausible incomplete control is frozen while the reference contract is unresolved.

**Environment.** Historical `.tool-versions` pins Elixir `1.15.6-otp-25`, OTP `25.0.2` and Node `16.15.1`; CI uses PostgreSQL 10. The Dockerfile instead uses Elixir `1.15.7`/OTP `26.1.2` and Node `16.19`, so record the tested runtime rather than treating both recipes as equivalent. PostgreSQL and native YAML dependencies remain. The app also starts a local LanguageTool server; its backend checks whether a Java JAR exists. Export does not itself require spelling, but startup/no-JAR behavior still needs fixture verification. Tests disable external Goth/Tesla integrations and telemetry UI. [Tool versions](https://github.com/mirego/accent/blob/98eb7f93dca39713e4c8557882c63437d36d748f/.tool-versions), [Dockerfile](https://github.com/mirego/accent/blob/98eb7f93dca39713e4c8557882c63437d36d748f/Dockerfile), [test config](https://github.com/mirego/accent/blob/98eb7f93dca39713e4c8557882c63437d36d748f/config/test.exs), [LanguageTool backend](https://github.com/mirego/accent/blob/98eb7f93dca39713e4c8557882c63437d36d748f/vendor/language_tool/lib/language_tool/backend.ex).

## 4. Duplicate collaborators and the later migration correction — #169

**Useful corrected-feature example, not a ready reference.** The PR adds normalized email validation plus a database constraint preventing duplicate email/project pairs. It also cleans existing duplicates. Original pair: `1097114eac629ab71fde0b2fcee26cd4cca3f394` → `c6ee149163b74cb664084234bc137a6c5251e3d7`. The original cleanup groups only by email, so a later membership in another project can be deleted despite being valid. This directly violates the preservation lesson from the rejected Plausible 6441 case. [PR #169](https://github.com/mirego/accent/pull/169), [original migration](https://github.com/mirego/accent/blob/c6ee149163b74cb664084234bc137a6c5251e3d7/priv/repo/migrations/20200430174230_unique_collaborator_email.exs).

Upstream then removed the dangerous cleanup in `25b690798de12259795394ffa244efc9abbf38d4` and restored a project-scoped cleanup in `ae755afa3952a87d013139f1f1e6e62ce3488c4b`. These are direct correction commits, not separate PRs. A proposed case could start before #169 and request the corrected behavior: reject repeated invitations within a project, normalize new email addresses, retain one oldest existing duplicate per project and preserve legitimate memberships in other projects. The original feature is a natural compiling incomplete control whose cross-project preservation assertion should fail. [Removal](https://github.com/mirego/accent/commit/25b690798de12259795394ffa244efc9abbf38d4), [scoped correction](https://github.com/mirego/accent/commit/ae755afa3952a87d013139f1f1e6e62ce3488c4b).

**Two unresolved holds.** First, the corrected SQL deletes only rows strictly later than the minimum `inserted_at`; same-project duplicates tied at that timestamp survive, so the unique index can still fail. This is a static reference challenge, not an executed result. A sound migration fixture must include same-time duplicates, different projects, ordinary memberships, role/user associations and post-migration valid/invalid invitations; declare a deterministic tie policy only if a specific surviving row is scored. Second, the eight-commit upstream interval includes unrelated pagination and release/dependency changes. Selecting only the feature and cleanup corrections would create a synthetic fixed tree; current exact-upstream reconstruction cannot simply label that tree with the later upstream SHA. Do not put unrelated source in a test/environment overlay. [Full interval](https://github.com/mirego/accent/compare/1097114eac629ab71fde0b2fcee26cd4cca3f394...ae755afa3952a87d013139f1f1e6e62ce3488c4b), [corrected migration](https://github.com/mirego/accent/blob/ae755afa3952a87d013139f1f1e6e62ce3488c4b/priv/repo/migrations/20200430174230_unique_collaborator_email.exs), [provenance requirements](../case-admission.md).

The historical runtime is the same broad Elixir 1.9/OTP 22/PostgreSQL 10 family as #183. The migration must be tested starting from a pre-migration database containing representative existing rows, not only a fresh empty schema followed by the upstream invitation tests. Do not promote the original or corrected reference without resolving the witness and provenance holds.
