# Community application candidates: Mobilizon — 2026-10-18

Mobilizon adds ordinary event-organizing and calendar workflows to the candidate pool. Two coordinated repairs merit further work: complete upcoming-event feeds and related-event recommendations that do not lose valid results. A small iCalendar status feature is a reserve. **All three remain deferred** because the current source validator accepts GitHub repositories and PR URLs, whereas their authentic upstream source is Framagit. None was imported, built, executed, qualified, or run against a model.

This pass follows the [selection guidance](../pr-selection-guidelines.md), [admission contract](../case-admission.md), and [rejection register](../../cases_rejected/README.md). None of these source identities occurs in the existing research notes or rejected cases. The feed and recommendation candidates both need mixed populations: excluding unwanted events must not also remove legitimate ones, the central preservation lesson from Plausible #6441. All commands in this pass retrieved or inspected source; no timing or performance evidence was collected.

## Product-purpose screen

Mobilizon is an application for communities to publish events and organize groups. Its current first-party site identifies Kaihuri as the maintainer since 2024; the old Framasoft source URL redirects to `kaihuri/mobilizon`. Its stated purpose and the selected workflows fit the requested ordinary-application category. This is a scoped product/source screen, not a security certification. [Project purpose and stewardship](https://mobilizon.org/about/), [canonical source](https://framagit.org/kaihuri/mobilizon).

The historical application contains optional Matomo, Plausible and Sentry integrations, so describing it as containing no analytics code would be inaccurate. At the inspected !1378 revision, the default analytics provider list is empty. Any future fixture should explicitly keep reporting integrations disabled and use local event fixtures with networking disabled. The selected cases exercise calendars and recommendations, not analytics or surveillance. [Default configuration](https://framagit.org/kaihuri/mobilizon/-/blob/96d397baf12525bd29e62a04289204cf167eeed9/config/config.exs#L362), [provider configuration](https://framagit.org/kaihuri/mobilizon/-/blob/96d397baf12525bd29e62a04289204cf167eeed9/lib/service/front_end_analytics/analytics.ex), [original analytics integration](https://framagit.org/kaihuri/mobilizon/-/merge_requests/1200).

## 1. !1378 — upcoming events across public and personal feeds

The original issue asks that ICS export contain upcoming events. The accepted repair handles public actor/group feeds and token feeds for one identity or all identities of a user. `events.ex` introduces upcoming-only queries; `export/common.ex` routes the export consumers through them. The controller tests exercise Atom and ICS output and add past-event fixtures alongside valid future events. This is application behavior across persisted events, identity boundaries and generated artifacts, rather than a generic library exercise. [Issue #1246](https://framagit.org/kaihuri/mobilizon/-/issues/1246), [accepted diff](https://framagit.org/kaihuri/mobilizon/-/compare/5ae2e2254aca18d4e473fd8c1805d5d3808eeef1...96d397baf12525bd29e62a04289204cf167eeed9), [controller tests](https://framagit.org/kaihuri/mobilizon/-/blob/96d397baf12525bd29e62a04289204cf167eeed9/test/web/controllers/feed_controller_test.exs).

- **Source pair:** broken `5ae2e2254aca18d4e473fd8c1805d5d3808eeef1`; fixed `96d397baf12525bd29e62a04289204cf167eeed9`. The broken revision is the accepted merge's first parent, verified from the commit API. It is not inferred from the MR's earlier diff base. [Accepted commit metadata](https://framagit.org/api/v4/projects/20125/repository/commits/96d397baf12525bd29e62a04289204cf167eeed9).
- **Draft visible contract:** “Public actor/group feeds and personal token feeds should include only events whose start time is still in the future. Apply this to ICS and Atom exports while preserving each feed's existing visibility and identity scope.” Explicitly stating start time matters: this reference filters `begins_on`, so it excludes an already-started multi-day event even if it has not finished. Do not silently grade a different ongoing-event policy. [Query implementation](https://framagit.org/kaihuri/mobilizon/-/blob/96d397baf12525bd29e62a04289204cf167eeed9/lib/mobilizon/events/events.ex), [export consumers](https://framagit.org/kaihuri/mobilizon/-/blob/96d397baf12525bd29e62a04289204cf167eeed9/lib/service/export/common.ex).
- **Discriminating checks:** request both artifact formats through the controller; parse entries; mix past and future events; exercise public person, public group, one-identity token and whole-user token feeds. Assert future entries remain present, not merely that past entries are absent. Preserve private/draft exclusions for public feeds and identity isolation for tokens. Use dates clearly separated from the clock boundary, and document the clock policy.
- **Plausible incomplete control:** switch the public feed path to upcoming queries but leave token feeds unchanged. It should compile and fail a named personal-feed assertion. A second useful challenge is a patch that drops all events; mixed positive fixtures must reject it.
- **Scope limit:** instance-wide feed selection is a separate function and is unchanged by this MR. Do not write “all feeds” and silently include instance-wide behavior. Ordinary non-feed historical-event APIs must retain past records; replacing their behavior globally is an overbroad repair. The reference also reorganizes the participation query, so preservation should include non-feed participation consumers.
- **Later-change screen:** [!1512](https://framagit.org/kaihuri/mobilizon/-/merge_requests/1512) later changes ordering and limits for instance feeds and ActivityPub listing. It is not automatically a correction required for the narrowly defined actor/token outcome above; combining it would enlarge the contract. Its full diff was inspected.

## 2. !1526 — preserve eligible related-event recommendations

[!1482](https://framagit.org/kaihuri/mobilizon/-/merge_requests/1482) first hid finished related events in the Vue view. The subsequent !1526 description explains the observable failure: the server selects four related events, then the browser removes finished ones, potentially leaving an empty section despite other eligible events. The correction filters in the related-event query and lets the view render the resulting list. The full two-file accepted diff was inspected. [Correction and rationale](https://framagit.org/kaihuri/mobilizon/-/merge_requests/1526), [accepted diff](https://framagit.org/kaihuri/mobilizon/-/compare/d25577ea5d907f828905846c9362582eae529078...54aa628403fb911ef90789944508854e9d3cf1a8).

- **Source pair:** broken `d25577ea5d907f828905846c9362582eae529078`; fixed `54aa628403fb911ef90789944508854e9d3cf1a8`. These are the accepted merge's first parent and accepted merge respectively. [Commit metadata](https://framagit.org/api/v4/projects/20125/repository/commits/54aa628403fb911ef90789944508854e9d3cf1a8).
- **Draft visible contract:** “An event's related-events section can become empty when its initially selected recommendations have finished, even though eligible related events remain. Show up to four eligible recommendations, excluding events whose end time has passed, or whose start time has passed when they have no end time. Preserve the existing visibility and relevance rules.” The ongoing-event rule is supported by both the original frontend predicate and the corrected backend's `coalesce(ends_on, begins_on)` predicate. [Corrected query](https://framagit.org/kaihuri/mobilizon/-/blob/54aa628403fb911ef90789944508854e9d3cf1a8/lib/mobilizon/events/events.ex#L1880), [original frontend predicate](https://framagit.org/kaihuri/mobilizon/-/merge_requests/1482/diffs).
- **Discriminating checks:** construct more than four related events, with finished events occupying the old selected set and future/ongoing events otherwise eligible. Query the actual GraphQL relation and assert positive eligible results as well as exclusions. Include ongoing events, no-end-time events, unrelated events and non-public/draft records. Control relevance ties with deliberately different fixture attributes; do not require an incidental ordering that the product never promised.
- **Boundary:** a GraphQL/database check can demonstrate the central defect. A mounted Vue interaction or offline browser witness should additionally verify that the resulting recommendations are displayed; merely checking that the old frontend filter disappeared would overconstrain the implementation. No tests changed upstream, so acceptance work is substantial and not yet done.
- **Plausible incomplete control:** retain frontend-only filtering or add a post-limit server filter. The latter can compile and correctly exclude finished events yet still fail the positive assertion that available future events fill the selected result set.
- **Feature-plus-fix option:** this is a concrete example of the user's proposed corrected-feature shape. A case starting before !1482 could require the final corrected recommendation behavior. However, !1482 and !1526 are months apart, and their whole upstream interval contains unrelated work. Prefer the clean !1526 repair pair now. Combining only selected feature/fix patches would need an explicit synthetic-source reconstruction recipe, plus separate source-provider support; it is not an ordinary single-MR import.

## 3. !1469 — calendar status, focused reserve

The accepted change passes an event's status into the iCalendar event and extends the expected exported artifact with `STATUS`. It has one substantive implementation line and one test expectation, so it should not be described as coordinated multi-file work. [MR](https://framagit.org/kaihuri/mobilizon/-/merge_requests/1469), [accepted diff](https://framagit.org/kaihuri/mobilizon/-/compare/da7a08d1305a39fe815fa95695ce338526ffb941...5681e6e8b8c7da0c91a82f2459fb5c02ac6ef684).

- **Source pair:** broken `da7a08d1305a39fe815fa95695ce338526ffb941`; fixed `5681e6e8b8c7da0c91a82f2459fb5c02ac6ef684`. [Commit metadata](https://framagit.org/api/v4/projects/20125/repository/commits/5681e6e8b8c7da0c91a82f2459fb5c02ac6ef684).
- **Draft contract:** “Export each event's status in its iCalendar representation, while preserving the other event details.” The curation step must enumerate the starting schema's supported statuses and make any required mapping visible. The single upstream expectation is not sufficient evidence for every supported status.
- **Checks/control:** export at least a cancelled and a confirmed event, parse the calendar status, and preserve UID, organizer, dates and description. A compiling partial solution that hard-codes `CONFIRMED` must fail the cancelled-event assertion. No requirement should force the reference's exact internal field assignment.
