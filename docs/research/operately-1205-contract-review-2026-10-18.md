## Requirements-first record, before accepted-diff inspection

The proposed solver ticket is: “Archived milestones still appear in a project’s milestones list. Exclude them while keeping active milestones visible and preserving the existing optional include behavior.” I read that ticket and the starting source/tests before opening the accepted diff. The earlier [candidate research](music-work-management-candidates-2026-10-18.md) already describes the broad upstream approach and accepted test scope; this review is requirements-first relative to new assertions, not wholly blind to reference commentary.

The concrete product boundary is authenticated `get_project` with `include_milestones: true`: the starting [milestones-page loader](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/assets/js/pages/ProjectMilestonesPage/loader.tsx) uses exactly that query. The [starting query](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/lib/operately_web/api/queries/get_project.ex) includes milestones through association preloading and asks the project getter to allow deleted projects. The [getter](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/lib/operately/repo/getter.ex) checks requester access and applies supplied after-load callbacks. The [Repo](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/lib/operately/repo.ex) normally filters schemas by nil `deleted_at`, but explicitly bypasses that filter under `with_deleted: true`.

Authorized outcomes derived from this starting behavior:

- Included milestones must contain every non-archived milestone belonging to the requested project, and no archived milestone or other project's milestone. “Active” here means not soft-deleted: the [milestone schema](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/lib/operately/projects/milestone.ex) separately represents pending/done status and `deleted_at`; completed non-archived milestones must remain visible.
- An included empty population, including an all-archived population, should serialize as an empty list. Omitted or false `include_milestones` should retain the unloaded association's nil serialization. Do not silently make inclusion unconditional.
- Retained milestones must remain usable: their identities and project identities must identify the right records, and existing title, status, dates, description and Kanban data should remain intact. No exact query strategy, helper name, order among milestones, or requirement to preload the inverse project association follows from the ticket.
- Preserve the normal authenticated/access-controlled request path and the existing ability to retrieve an archived project. The [starting project tests](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/test/operately_web/api/queries/get_project_test.exs) explicitly exercise the latter. Hiding the whole archived parent is not a correct general repair.
- Retrieval must remain read-only. Milestone archiving already soft-deletes through [Projects.delete_milestone/2](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/lib/operately/projects.ex); it does not authorize deleting or modifying records merely to conceal them in a response.

The minimal visible brief can remain the proposed ticket. Appended requirements may clarify that active means non-archived regardless of completion status, that optional inclusion stays optional, and that the response contains only the selected project's milestones. They should not silently expand the task to a universal soft-delete audit, a new archive/delete workflow, or every unrelated list endpoint. The existing plural `get_projects` API and direct milestone retrieval are useful preservation boundaries, but this page's singular project result is the required regression witness. No new `next_milestone` calculation follows from this ticket: the singular getter does not run the project's plural-list after-load hook by default.

**Checkpoint:** the outcomes above were recorded before inspecting the accepted diff or any new acceptance artifact. No static fixture approval, runtime result or final admission is claimed.

## Primary issue, accepted repair and reference limits

[Issue 1200](https://github.com/operately/operately/issues/1200) identifies the Project Milestones page and was closed by [PR 1205](https://github.com/operately/operately/pull/1205) on September 27, 2024. Its brief body adds no broader behavior requirement. The accepted [commit](https://github.com/operately/operately/commit/ef2bac5edc50f8490e98fd7fecaa52a975e9434e) is a single-parent squash whose parent is exactly the proposed starting revision. The primary issue/PR conversation does not add ordering, new milestone status semantics, or a universal archive filter requirement. A bounded GitHub issue search for archived milestones returned this pair; inspection of project-module history through the end of 2024 found no separately identified follow-up to this fix. This does not establish absence of every later regression.

The full accepted diff changes five runtime files and three test/support files. Two runtime paths are substantive: `GetProject` moves milestone inclusion from the initial preload into an optional after-load callback, and `Project.load_milestones/1` separately preloads milestones and attaches the already loaded parent to each result. The helper alias and check-in/retrospective call-site alias changes are incidental. The existing boolean include helper replaces a local callback-filtering helper; it still excludes omitted and false flags. Other callback behavior remains intact, and privacy loading already ensures its own access-level prerequisite.

The root-cause inference follows the pinned Ecto 3.12.3 [preloader source](https://github.com/elixir-ecto/ecto/blob/v3.12.3/lib/ecto/repo/preloader.ex): query preloads receive the query's repository options and reuse them for association queries. Consequently the initial project fetch's `with_deleted: true` can allow archived milestone rows too. A separate preload uses the Repo's ordinary soft-delete filtering. The reference deliberately retains access to archived parent projects while filtering their children. This is source-supported analysis, not a reproduced runtime result.

**There is no serializer edit in the accepted diff.** The unchanged [milestone serializer](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/lib/operately_web/api/serializers/milestone.ex) computes `project_id` using `milestone.project`; simply loading milestones without the inverse parent would make ordinary serialization fail. The accepted loader's `%{milestone | project: p}` supplies that required data without re-querying a potentially archived parent. This is important reference coupling, but checks should require correct serialized identities/data rather than that exact assignment or preload strategy. Exact display-comment prefixes in IDs should not replace record identity as the contract witness.

The upstream added API test covers omission, two active milestones, then archiving one while retaining the other. It calls the real query and compares serialized records; the factory additions preload their project for that expected serialization. It does not independently cover all-archived/empty results, false inclusion, completed active milestones, foreign project isolation, archived-parent preservation, or rich milestone data. Those are justified bounded preservation cases from the starting behavior, not instructions to imitate the new helper. The accepted implementation appears to satisfy them statically. No material defect in the reference's intended request path was found.

One reference limit should remain explicit: `Project.load_milestones/1` does not force a reload of an association already loaded with archived rows. The accepted request path avoids that situation by removing its original preload. A hidden test that directly calls this new helper with a deliberately stale/preloaded association would impose a new helper contract and could reject the accepted solution. Likewise, the unchanged plural `get_projects` query has its own `include_archived` behavior; testing a new universal archived-child policy there would broaden this singular-page repair.

## Suggested request witnesses and compiling partial

Use the existing [TurboCase](https://github.com/operately/operately/blob/784ec4d6bca669b9b48af1152024d2d1d21e02dc/test/support/turbo_case.ex) request helper, which dispatches a real GET through `OperatelyWeb.Endpoint` to `/api/v2/get_project` and parses the JSON response. Log in through existing account helpers; do not invoke the loader as a substitute for the endpoint. Recommended discriminating cases are:

- Mixed population: two local non-archived milestones, one pending and one done, alongside archived rows and another project's rows. Compare the exact unordered retained ID set and cardinality. Check representative retained payload values independently of the implementation serializer, including project identity, title/status and populated dates or description/Kanban fields. A result that hides everything or only keeps pending rows must fail.
- Include semantics: omitted and false inclusion yield nil even when rows exist; true inclusion returns `[]` when none remain or none were created. Unrelated project fields and optional includes should continue working.
- Archived parent preservation: an accessible archived project remains retrievable and its included milestones still exclude archived children. Existing authentication and access tests should remain protected. Read-only retrieval must not change saved active/archived rows; use `with_deleted: true` for before/after snapshots where necessary.

The most informative partial control is the accepted runtime repair **with the original `include_milestones: [milestones: :project]` entry retained in `GetProject.preload/1`**. It contains the new callback and all required aliases/functions, so it is a coherent compiling incomplete change. Ecto's [documented preload behavior](https://hexdocs.pm/ecto/3.12.3/Ecto.Repo.html#preload/3) and pinned implementation preserve already loaded associations unless forced. The callback therefore sees cached archived children, and mixed/all-archived assertions should fail while active-only and omitted inclusion remain plausible. Qualification must confirm compilation and named assertion failures; this review does not claim that execution.

The earlier candidate note suggested filtering only a direct milestone query. Starting direct getters already use the normal soft-delete filter, so such a control could be a largely redundant edit. Retaining the old nested preload is a closer partial of this actual repair and better exposes the missing step. Do not use a partial that merely omits the inverse parent association: that tends to fail during serialization rather than demonstrate a wrong returned population.
