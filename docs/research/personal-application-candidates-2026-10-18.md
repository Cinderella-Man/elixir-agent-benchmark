# Personal and media application candidates — 2026-10-18

This pass investigated actual bookmark, video/community and game workflows. The strongest source leads are Algora TV's popout chat and soft video deletion, plus a historical playable ExVenture game's room-scanning command. Linkhut is an especially good product-purpose match, but its canonical SourceHut history does not satisfy the current GitHub-PR provenance contract without additional support. These are inspected candidates, not admitted cases: no builds, tests, qualification rounds, model attempts or performance measurements were run.

The selection follows the repository's [guidelines](../pr-selection-guidelines.md) and [admission contract](../case-admission.md). The [rejected-case register](../../cases_rejected/README.md) and earlier research were checked; none of the source identities below repeats those exclusions. In particular, preservation checks must prevent a repair from hiding all videos, dropping all messages or suppressing every adjacent room.

### Algora TV #77 — deleted videos disappear while their records remain

**Candidate brief:** “Deleting a video should hide it from the application's video listings and direct video lookup, while retaining its database record for later storage cleanup. Keep all undeleted videos and their existing visibility, ordering and channel/show filtering behavior.” The brief must state the retained-record policy; simply asking to “delete videos” leaves physical and logical deletion equally plausible.

The [accepted change](https://github.com/algora-io/tv/commit/71d883fe457b8995972e797953013932f80d98bf) adds a deletion timestamp to the schema and database, changes the delete operation, and filters several consumers: global lists, live/short videos, channel/studio/show lists, ID-ordered lists, latest-video lookup, direct lookup and interrupted-stream selection. The coordinated relationship is durable state and every affected reader, not repeated edits being counted as separate difficulty. The exact [library source](https://github.com/algora-io/tv/blob/71d883fe457b8995972e797953013932f80d98bf/lib/algora/library.ex) confirms that the ID-list reader removes absent results while preserving requested order.

**Proposed behavioral evidence:** create a mixed population of public/unlisted, deleted/undeleted videos across two channels and a show. Delete through the existing application operation, verify the row remains, then check representative public, studio, show and direct-lookup boundaries. Verify ordering of an ID list containing deleted, missing and surviving IDs. Preserve unrelated videos, messages/subtitles linked to the retained row, and existing visibility rules. Any interrupted-stream check should use controlled local fixtures, not real streaming or a wall-clock wait.

**Incomplete control:** persist the deletion marker and hide videos on the homepage only; it must still fail a named studio/direct-lookup assertion. **Unchanged control:** the original delete physically removes the record. Checks should assert through existing operations and `Repo.get` before inspecting the marker; constructing a new `%Video{deleted_at: ...}` in protected tests would fail to compile on the starting source and would be invalid discrimination.

**Evidence limits:** there are no upstream regression tests in this PR. Later changes to `library.ex` were inspected by path history; none was identified as a direct soft-deletion correction in that bounded review. This is not proof of reference correctness. No local database or application was started.

### Algora TV #83 — a real popout chat window

The [originating issue #80](https://github.com/algora-io/tv/issues/80) asks for a popout that can send and receive messages live, while the original chat remains available. A suitable clarified brief is: “Let viewers open the current video's chat in a separate window. Signed-in viewers can send messages there, both windows receive new messages, existing deletion permissions still apply, and the original chat remains usable.” Anonymous viewing and cross-video isolation should follow the existing application behavior; any stronger handling of forged anonymous events must be reviewed against the reference before becoming a scored requirement.

The [accepted change](https://github.com/algora-io/tv/commit/824c2931f27e33a9616ab261e64d14e19c553771) connects a TypeScript click hook, the video's menu, a route with current-user initialization, and a new LiveView subscribing to the same per-video chat topic. The new view uses existing message creation, permission checks, deletion and broadcast functions. This is a mixed Elixir/browser case; treating the hook as an incidental UI detail would omit part of the requested feature.

**Proposed behavioral evidence:** launch the actual local video page, click the popout, assert that a second page opens to that video's chat, then send a message and observe it in both windows. Use a second video's chat as a negative preservation case. Exercise deletion by the author or channel owner, and reject another ordinary user's delete event. Verify persistence and a fresh mount, so a UI-only echo cannot pass. Use fixed local users, sessions, videos and avatars, with no GitHub OAuth or real media delivery.

**Incomplete control:** add the popup route and initial message rendering but omit the live subscription; a message created after mounting must fail the named cross-window delivery assertion. A separate useful partial control omits posting while allowing reads. **Unchanged control:** the original video page has no popout action; fail that named assertion in the test body rather than treating a missing new route as setup failure.

**Reference concerns to resolve:** no tests were added. The hook appends `/chat_popout` to the whole `window.location.href`, so a video URL with a query or fragment needs a deliberate reference challenge before those forms are promised. Its cleanup references a handler different from the anonymous listener; do not silently require a lifecycle guarantee that was never checked. The anonymous page hides the send form, but the event callback is not itself guarded before calling the typed chat creation function. These are reasons to examine the reference, not to add invisible requirements. The path history for `chat_popout.ex` returned only this introduction, so no later correction was found for those concerns.

### ExVenture #46 — see nearby characters without seeing through closed doors

**Candidate brief:** “Add a `scan` command that shows NPCs and players in the current room and each adjacent room you can see into. Closed doors block the adjacent room, empty adjacent rooms are omitted, and scanning does not move the player.” `scan` is the requested public command, not a leaked internal symbol.

The [accepted change](https://github.com/oestrich/ex_venture/commit/00ded098c35ff8bb44e64a80b2185e2a6e9dc065) wires command dispatch, implements traversal/door filtering, and formats the results. `game/door.ex` changes formatting only and is excluded from the substantive count. Two test files cover command parsing, the current room, an open adjacent room and a closed adjacent room. Existing fixtures use a test room environment and socket recorder; those are source-established seams, not new mocks replacing the behavior under test.

**Proposed behavioral evidence:** retain the upstream examples, add an empty adjacent room and a room containing both an NPC and another player, and assert direction labels plus unchanged player location. Drive the existing command dispatcher so implementations are not forced to introduce the reference module. Avoid adding an unconditional `doctest Game.Command.Scan` to the unchanged-control overlay: the new module is absent initially and that would cause compilation failure instead of a named behavioral failure.

**Incomplete control:** show the current and adjacent populations but ignore door state; the blocked-room assertion fails while positive checks still pass. Another plausible partial solution only shows the current room and must fail the open-adjacent-room check.

**Later history:** the [2018 door-state correction](https://github.com/oestrich/ex_venture/commit/74ca32846a0e29f21cc4ef0074b06d068b6854b5) checks `has_door` before querying the shared `door_id`. It follows a changed exit representation; the original #46 uses exit IDs and treats unknown cache entries as not closed. Do not graft that later patch onto #46 or demand later overworld/door-model behavior from the old task. No execution established that the original reference passes a broader fixture set.

### ExVenture #26 — corrected speech syntax, held lineage

The [feature PR](https://github.com/oestrich/ex_venture/pull/26) extends speech parsing, room/channel delivery, message structures and output formatting with a phrase such as `[softly]`. Five test files include both new parsing/formatting examples and updates to NPC/session behavior. It is a player-expression workflow across parser and consumers, not a templating-library benchmark.

The original implementation searches for brackets anywhere in the message. A later [accepted correction](https://github.com/oestrich/ex_venture/commit/4e23812d0190a27a5793254285a4930282d970db) restricts the phrase to the beginning after trimming whitespace, and adds a test preserving `hello [softly]` as ordinary speech. Correction pair: `b23a64acce2720deaf0e48615bb30516ef50cbe8` → `4e23812d0190a27a5793254285a4930282d970db`. GitHub's commit-to-PR lookup returned no associated PR for this correction.

**Corrected-feature brief:** “Support an optional leading bracketed manner phrase in player speech, including directed speech and channels. Display the phrase with the speech attribution, preserve ordinary speech and target resolution, and leave bracketed text later in the message as spoken text.” This states the later product policy rather than hiding it in a parser test. Keep multiple bracket groups and malformed bracket syntax out of the contract until reviewed; the reference regex remains greedy.

**Controls:** the original #26 feature is a natural incomplete solution because it consumes trailing bracketed text. Check the speaking player's echo, another recipient's formatted message, directed-target resolution, channel delivery and unchanged NPC reactions. A partial implementation that only changes the sender's local echo must fail recipient checks. Do not require the new internal struct fields in tests compiled against the pre-feature source.

**Disposition:** do not admit #26 unchanged. Combining the old feature with its correction is semantically coherent, but the intervening history includes other changes and the correction was not a PR. A synthetic composed reference needs explicit provenance/reconstruction support; no composition or reconstruction was performed here. This is a supplementary lineage for the user's feature-plus-fix question, not an immediate source bundle.

## Linkhut — strong purpose match, source-support holds

### URL lookup decodes percent-encoded content twice

The [mirrored accepted commit](https://github.com/sourcehut-mirrors/linkhut/commit/513ee57c2c43db85d38e3869eca998ce693d729d) changes two controllers, with no test changes. Pair: `5d8ea557ede0b58cf715620fa4d13f2678f2dec5` → `513ee57c2c43db85d38e3869eca998ce693d729d`. It removes a second URL decoding step from bookmark list context and URL-detail lookup. The authored commit message identifies URLs containing fragments and percent-encoded characters as the trigger.

**Candidate brief:** “Bookmark and URL-detail lookups fail for saved URLs containing escaped characters or fragments; fix both views while preserving ordinary URLs.” Tests should issue actual encoded HTTP requests and verify selected bookmarks through both the global and user-scoped views, rather than call a controller with already-decoded hand-built parameters. Include a saved escaped URL and a distinct near-match so a normalization change cannot falsely merge them. An incomplete repair touching only one controller should compile and fail the other route's assertion. The upstream patch is small but coordinates two real user entry points.

**Hold:** the [official site](https://linkhut.org/) points to SourceHut, and pinned [project metadata](https://github.com/sourcehut-mirrors/linkhut/blob/513ee57c2c43db85d38e3869eca998ce693d729d/mix.exs) names `https://git.sr.ht/~mlb/linkhut`. The canonical commit page returned HTTP 418 in this research environment; the mirror's hash has not been independently matched to the canonical Git repository. No GitHub PR exists to use as current provenance. Verify the canonical object and implement/review SourceHut commit/issue provenance support before preparing a case; do not invent a PR or label the mirror canonical.

### Interrupted bookmark imports

The later [mirrored commit](https://github.com/sourcehut-mirrors/linkhut/commit/7eff26d92d7b04562f7f88ee3bf095ca5731e407), linked by its author to [SourceHut issue #65](https://todo.sr.ht/~mlb/linkhut/65), records a richer workflow: retries, atomic bookmark/progress persistence, atomic job creation, and reconciliation of stranded imports. Pair: `f972cc977c72c5d5ea3ad0a4b229ffe19d1a3df1` → `7eff26d92d7b04562f7f88ee3bf095ca5731e407`. This is a **discovery reserve**, not a fully inspected candidate: file inventory and authored rationale were inspected, but not the complete implementation and reference behavior.

Its scope is larger than the preferred group: application configuration, context/schema, worker replacement and a reconciler, controller and migration, plus one test file and two documentation files. It deserves separate investigation after source support exists. The needed boundary is restart/retry correctness with deliberate transaction failures and deterministic worker/reconciler invocation; never grade faster completion or run throughput tests. A partial fix that only retries jobs can duplicate already-imported bookmarks or lose progress, making a useful future control.
