## Requirements-first record

This section was written after reading the proposed solver-visible ticket and starting source/tests, before inspecting the accepted diff or PR. The pre-existing [candidate research note](music-work-management-candidates-2026-10-18.md) was also read for product purpose/licensing; that note includes a reference summary and proposed witness, so this review is independent of hidden assertions but is **not blind to all prior reference commentary**.

Proposed ticket:

> Posting a project check-in can create duplicate notification subscriptions when the same person is selected or mentioned more than once, including the author. Keep one subscription per person, preserve every distinct intended recipient, and keep explicitly invited recipients invited even when they are also mentioned. Posting without an explicit recipient list must still work.

Starting revision: `4a223d0077e0027219546d184115b9fe1dc9d1a9`.

The ticket and starting implementation authorize these observable outcomes:

1. Posting through the authenticated project-check-in mutation succeeds with valid overlapping populations and persists a check-in. The existing mutation, authorization checks, serialized response and transaction establish that application boundary; a new internal helper interface is not required. [Starting mutation](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/lib/operately_web/api/mutations/post_project_check_in.ex), [starting API tests](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/test/operately_web/api/mutations/post_project_check_in_test.exs).
2. For each posted check-in, the persisted subscription list contains exactly the distinct union of its author, explicitly selected people and valid rich-text mentions, with one subscription per person. Repetition within the selected list, repetition within mentions, author overlap, and selected/mentioned overlap are all within the ticket. Unrelated people must not become subscriptions merely to satisfy a row count. The starting operation inserts the author separately and creates selected and mentioned subscriptions under different transaction keys, while deduplicating only mentions. [Starting operation](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/lib/operately/operations/project_check_in.ex).
3. Explicit selection takes precedence over mention-only status. The author remains invited because the starting operation gives the author `:invited`; a mention-only recipient remains `:mentioned` because that distinction is existing behavior in the same code and persisted schema. [Starting operation](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/lib/operately/operations/project_check_in.ex), [subscription schema](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/lib/operately/notifications/subscription.ex).
4. An omitted explicit recipient list and an empty list both remain valid. Neither implies suppressing the author or mentions. The mutation currently accepts omitted `subscriber_ids` using `:allow_nil`; the starting operation has a nil clause and existing API tests omit this field. Explicit JSON null is a natural equivalent at this boundary but should be stated if independently scored beyond omission/empty-list coverage. [Starting mutation](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/lib/operately_web/api/mutations/post_project_check_in.ex), [starting API tests](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/test/operately_web/api/mutations/post_project_check_in_test.exs).
5. Existing check-in/list association, `parent_type: :project_check_in`, `parent_id`, per-check-in isolation, and the caller's `send_notifications_to_everyone` setting must survive. These are direct preservation checks of the operation being repaired, rather than new notification delivery requirements. [Starting operation](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/lib/operately/operations/project_check_in.ex), [subscription-list schema](https://github.com/operately/operately/blob/4a223d0077e0027219546d184115b9fe1dc9d1a9/lib/operately/notifications/subscription_list.ex).

Not authorized by this brief: exact helper/module names or insertion order; a unique database constraint; retroactive cleanup of existing rows; global uniqueness across different check-ins; deduplication across simultaneous separate requests; exact email/notification counts; new invalid-ID, cross-company, permission, mention-parser, or frontend requirements. Existing permission and ordinary no-mention behavior may be preserved using baseline tests. Browser/cloud access is unnecessary for this API persistence contract.
