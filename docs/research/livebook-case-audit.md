# Livebook case audit — 2026-10-14

Historical audit of the original twelve-case revision. The audited inputs are preserved in [the original fixture archive](../../verification/task-quality/original/README.md); the [subsequent promotion](../verification/task-quality-promotion-2026-10-14.md) applies the findings to the eleven-case v3 inventory.

**Runtime follow-up:** see the [completed execution report](../verification/task-quality-audit-2026-10-14.md) for final decisions and named failures. This document preserves the source-review reasoning and its pre-execution judgments.

All six Livebook tasks are worth retaining as task ideas. The present fixtures are not equally strong evidence that an arbitrary passing repair satisfies the ticket. The clearest gaps are text/append coverage in 2219, overly specific diagnostic snapshots in 2800, import-set fidelity and subsequent execution in 2822, and missing failure-path validation in 3076. 2527 and 2663 already have useful positive/negative pairs, but targeted independent variants improve confidence. These are source-review judgments, not executable qualification verdicts. The current evaluation contract explicitly requires execution of unchanged, reference, incomplete, and integrity controls. [Evaluation contract](../evaluation.md), [existing validation status](../validation-2026-10-14.md).

## Evidence and limits

This review read every Livebook ticket, manifest, implementation patch, acceptance patch, reference-test patch and available upstream-test patch. It also read the corresponding exact historical source snapshots, including the full targeted test files and the implementation call paths. Source snapshots were obtained from the recorded-revision archives under `.local/task-audit/sources/`; 24 selected files were independently fetched from the same revisions on `raw.githubusercontent.com` and byte-compared successfully with the archives. The historical before/after identifiers are recorded per case in `provenance.json`. No model, Docker, build, functional suite or speed measurement was run by this review worker. Patch applicability, exact mutation replacement counts and Elixir syntax parsing were checked; those checks do not establish that the proposed tests compile or pass. [2219 provenance](../../verification/task-quality/original/cases/livebook-pr-2219/provenance.json), [2527 provenance](../../verification/task-quality/original/cases/livebook-pr-2527/provenance.json), [2663 provenance](../../verification/task-quality/original/cases/livebook-pr-2663/provenance.json), [2800 provenance](../../verification/task-quality/original/cases/livebook-pr-2800/provenance.json), [2822 provenance](../../verification/task-quality/original/cases/livebook-pr-2822/provenance.json), [3076 provenance](../../verification/task-quality/original/cases/livebook-pr-3076/provenance.json).

The upstream PR pages were consulted where available. A PR's merge establishes historical provenance, not oracle completeness. In particular, upstream testing can intentionally focus on one reproduction because the maintainers also review implementation; a benchmark grants a pass to arbitrary submitted implementations and needs stronger behavioral discrimination. The individual judgments below derive from the local executable fixtures and exact upstream code, not from assumptions about whether the upstream authors wrote enough tests. [2527 PR](https://github.com/livebook-dev/livebook/pull/2527), [2663 PR](https://github.com/livebook-dev/livebook/pull/2663), [2800 PR](https://github.com/livebook-dev/livebook/pull/2800), [2822 PR](https://github.com/livebook-dev/livebook/pull/2822), [3076 PR](https://github.com/livebook-dev/livebook/pull/3076).

Independent proposed tests and exact source mutations are retained in the tracked [task-quality verification cases](../../verification/task-quality/cases). Each directory contains an `audit.json` and a supplemental `acceptance.patch` that adds a standalone test file. The supplemental patches apply after the existing acceptance patches. The [2800 directory](../../verification/task-quality/cases/livebook-pr-2800) additionally contains `replacement-acceptance.patch`, a replacement for the original acceptance overlay, and a positive alternative implementation specification. These are review/execution inputs; they are not silently part of the scored release. Authoring copies under `.local/task-audit/proposals/` are disposable; the tracked patches are canonical.

## 2219 — inputs introduced by frame updates

Executable audit inputs: [supplemental checks](../../verification/task-quality/cases/livebook-pr-2219/acceptance.patch), [mutation specifications](../../verification/task-quality/cases/livebook-pr-2219/audit.json).

The ticket is unusually useful because it states a visible symptom, the immediate expected label/default, and the required integration path. The accepted implementation touches output indexing, input discovery and LiveView component updates; it also changes the return shape of a notebook helper and updates the separate app-session consumer. This is a legitimate repository-navigation task rather than a pure helper-function exercise. The important observable requirement is rendering the right inputs after a frame update; the helper's new tuple shape is one implementation strategy and should not become a hidden grading requirement. [Ticket](../../verification/task-quality/original/cases/livebook-pr-2219/ticket.md), [reference implementation](../../verification/task-quality/original/cases/livebook-pr-2219/reference.patch), [fixed session implementation](https://github.com/livebook-dev/livebook/blob/2a71e49d76fb24b386bb067a9e5d1bd1d6e44e66/lib/livebook_web/live/session_live.ex).

| Ticket requirement | Existing observation | Gap / proposed observation |
| --- | --- | --- |
| New text input displays its label and default immediately | New test sends a `:number` input into an empty frame with `:replace`, then asserts label and value `1` | Add the stated `:text` example (`Name` / `Jane`) and assert an input element of text type |
| No unrelated interaction is needed | The test sends output, waits for session synchronization and renders to drain the component update | Preserve this synchronization; do not “fix” the test by editing another cell or changing notebook state |
| Existing inputs retain ordinary behavior | Existing session suite tests editing ordinary numeric inputs and several other input paths | Exercise editing the newly inserted text input, append another input, then assert the edited value remains and both session values exist |
| Existing outputs survive updates | Existing test covers replacement of terminal text | Add a nested frame update with an unaffected sibling terminal output |

The current new test checks a DOM value but does not establish that text values survive append, repeated updates or normal editing. `FrameComponent` has distinct append/replacement behavior and temporary output assigns, while `InputComponent` reads its value from `input_views`; these are concrete state boundaries worth exercising. The proposed text-edit-append test reaches both components through the session API and checks the emitted change event. [Acceptance patch](../../verification/task-quality/original/cases/livebook-pr-2219/acceptance.patch), [historical frame component](https://github.com/livebook-dev/livebook/blob/64dad900d7890389f6f59edf4d6dbbdb725bcb26/lib/livebook_web/live/output/frame_component.ex), [historical input component](https://github.com/livebook-dev/livebook/blob/64dad900d7890389f6f59edf4d6dbbdb725bcb26/lib/livebook_web/live/output/input_component.ex), [historical session tests](https://github.com/livebook-dev/livebook/blob/64dad900d7890389f6f59edf4d6dbbdb725bcb26/test/livebook_web/live/session_live_test.exs).

The existing partial repair applies only `notebook.ex`, testing that bookkeeping alone is insufficient. The new `numeric-inputs-only` mutation filters frame-discovered inputs to numeric inputs, preserving exactly the type used by the current new acceptance test. Rejecting it is stronger evidence that the ticket's text requirement is covered. The nested-frame check also tests recursive discovery. Neither mutation result is assumed before execution. [Manifest partial probe](../../verification/task-quality/original/cases/livebook-pr-2219/case.json), [cell input discovery](https://github.com/livebook-dev/livebook/blob/2a71e49d76fb24b386bb067a9e5d1bd1d6e44e66/lib/livebook/notebook/cell.ex).

The fixture deliberately omits the upstream notebook-helper return-shape assertions from curated tests. That is defensible: requiring a particular helper return shape would reject alternative correct solutions. Likewise the ticket specifies notebook sessions, so app-session behavior should either be stated as part of the task and tested, or documented as outside this case's scored scope. The upstream implementation touching it is not sufficient reason to add a hidden app-only requirement. [Exact upstream tests](../../verification/task-quality/original/cases/livebook-pr-2219/upstream-tests.patch), [curated reference tests](../../verification/task-quality/original/cases/livebook-pr-2219/reference-tests.patch).

## 2527 — altered signed notebooks

Executable audit inputs: [supplemental checks](../../verification/task-quality/cases/livebook-pr-2527/acceptance.patch), [mutation specifications](../../verification/task-quality/cases/livebook-pr-2527/audit.json).

This is a good narrowly framed authorization task: it requires denying authorization after insertion and continuing to accept unchanged signed notebooks. The original implementation verifies a signed prefix selected by the stamp offset but does not validate that the remaining parsed source is only that stamp. The reference splits at the byte offset, parses the suffix and requires it to contain exactly the selected stamp before verifying the prefix. A blanket rejection of all stamps is therefore incorrect and already represented by the partial probe. [Ticket](../../verification/task-quality/original/cases/livebook-pr-2527/ticket.md), [reference patch](../../verification/task-quality/original/cases/livebook-pr-2527/reference.patch), [manifest](../../verification/task-quality/original/cases/livebook-pr-2527/case.json).

| Ticket requirement | Existing observation | Gap / proposed observation |
| --- | --- | --- |
| Inserting executable content before the stamp invalidates verification | Added test inserts an Elixir cell into a fixed signed fixture | Add dynamically signed Unicode notebook and both Elixir and Erlang inserted cells |
| Invalidated stamp grants no secret authorization | Added test asserts `hub_secret_names: []` | Retain; also assert the inserted cell remains imported, so dropping content is not a substitute for fixing verification |
| Verification failure is reported | Added test requires false verification plus warning | Retain meaningful warning assertion without requiring the whole wording |
| Legitimate signatures still work | Existing suite covers personal v2, personal v1 and offline-team stamps | Add a newly exported stamp and harmless whitespace between signed prefix and final stamp |

The target file already contains substantial positive coverage: personal v1/v2 signatures and an offline hub signature restore authorized secret names, and invalid tokens produce warnings. This is stronger than an isolated “reject modified document” test. However, a repair that looks only for literal Elixir fences in the suffix can satisfy the single new example without establishing the intended boundary. The `reject-elixir-fences-only` mutation makes that hypothesis executable. The `character-offset-instead-of-byte-offset` mutation distinguishes byte-based authenticity from character slicing; the generated Unicode title makes that difference observable. [Acceptance patch](../../verification/task-quality/original/cases/livebook-pr-2527/acceptance.patch), [historical import tests](https://github.com/livebook-dev/livebook/blob/57ddb291598b4ac5683fd71bd7a1454b621091e4/test/livebook/live_markdown/import_test.exs), [export stamp offset calculation](https://github.com/livebook-dev/livebook/blob/57ddb291598b4ac5683fd71bd7a1454b621091e4/lib/livebook/live_markdown/export.ex).

The generated positive test uses the application's exporter and then separately asserts import verification; it does not calculate an expected signature using the implementation being tested. Existing static upstream signatures remain useful independent evidence. The test permits whitespace because the accepted suffix parser trims it, and the signed prefix remains unchanged. This checks that a repair does not overreject a harmless representation variation. [Fixed suffix parser](https://github.com/livebook-dev/livebook/blob/94a0aedfda5d518997359a976f135dd0c12724e9/lib/livebook/live_markdown/import.ex).

Do not describe this case as comprehensive notebook security verification. Malformed JSON, negative or noninteger offsets, unsupported future stamp versions, duplicate stamps and all remote-file policies are separate contracts. This case can support the specific insertion/authorization claim with explicit valid-input preservation; it cannot prove absence of every signature-processing vulnerability. The narrower scope follows the actual ticket and selected functions. [Ticket](../../verification/task-quality/original/cases/livebook-pr-2527/ticket.md), [postprocessing logic](https://github.com/livebook-dev/livebook/blob/94a0aedfda5d518997359a976f135dd0c12724e9/lib/livebook/live_markdown/import.ex).

## 2663 — long numbered-list round trips

Executable audit inputs: [supplemental checks](../../verification/task-quality/cases/livebook-pr-2663/acceptance.patch), [mutation specifications](../../verification/task-quality/cases/livebook-pr-2663/audit.json).

This case has a clear invariant and relatively little environment risk: parse, format and parse again without changing list structure. The original renderer uses a constant continuation indent for ordered lists; the accepted implementation varies it by the rendered marker width. The current benchmark already improves on the exact upstream test by adding three-digit parents and repeated formatting, and explicitly requires that additional test identity. [Ticket](../../verification/task-quality/original/cases/livebook-pr-2663/ticket.md), [reference patch](../../verification/task-quality/original/cases/livebook-pr-2663/reference.patch), [acceptance patch](../../verification/task-quality/original/cases/livebook-pr-2663/acceptance.patch), [manifest required check](../../verification/task-quality/original/cases/livebook-pr-2663/case.json).

| Ticket requirement | Existing observation | Gap / proposed observation |
| --- | --- | --- |
| Two-digit parent preserves nested bullets and fenced code | Exact output for children under 10 and code under 11 | Put nested content on both sides of a decimal boundary |
| Three-digit parents work | Explicit extra test for 100 and 101 | Test nested children under 99 and code under 100 in the same document |
| Single-digit/unordered formatting remains correct | Existing suite covers basic, spaced, nested and block-content ordered/unordered lists | Retain those original tests |
| Repeated formatting is stable and preserves structure | Extra 100/101 check compares exact first render and repeated output | Also compare parsed semantic trees before and after, stripping location metadata |

The extra proposed document contains 105 items and nested bullets/grandchildren at 9/99, with fenced code at 10/100. It compares tree structure and checks idempotence. These assertions distinguish a stable but incorrectly flattened result from a structure-preserving round trip. The `extra-space-before-decimal-boundary` alternative uses the next number's width at 9/99. That extra space may still preserve nesting; it is deliberately a positive fairness control, not a required rejection. A semantic oracle should permit harmless additional indentation. The current partial probe remains the negative control for two-digit-only repairs; no second structural defect is asserted merely from a different rendered indent. [Historical formatter and tests](https://github.com/livebook-dev/livebook/blob/6f7a8e3e79db9a002b5c2508d817402b7c11ccb5/lib/livebook/live_markdown/markdown_helpers.ex), [existing list preservation tests](https://github.com/livebook-dev/livebook/blob/6f7a8e3e79db9a002b5c2508d817402b7c11ccb5/test/livebook/live_markdown/markdown_helpers_test.exs), [partial probe](../../verification/task-quality/original/cases/livebook-pr-2663/case.json).

There is some format specificity in the existing exact strings. Here it is less problematic than in 2800: the historical tests already establish a canonical formatter, including ordered marker numbering and unordered marker style. Nonetheless a semantic assertion is the better independent check of the ticket's nesting claim. Do not infer correctness just because formatting twice gives the same output; a formatter that drops children on the first pass is also idempotent. [Historical rendering test convention](https://github.com/livebook-dev/livebook/blob/6f7a8e3e79db9a002b5c2508d817402b7c11ccb5/test/livebook/live_markdown/markdown_helpers_test.exs).

## 2800 — Erlang diagnostics

Executable audit inputs: [supplemental checks](../../verification/task-quality/cases/livebook-pr-2800/acceptance.patch), [mutation specifications](../../verification/task-quality/cases/livebook-pr-2800/audit.json).

This is an authentic cross-runtime integration failure. The upstream PR explains that an error snippet had the wrong shape for the exception formatter; the repair returns source text instead. The ticket gives three reproducible errors and asks for the original diagnostic, source line and location, while preserving ordinary runtime-error reporting. [Upstream explanation](https://github.com/livebook-dev/livebook/pull/2800), [ticket](../../verification/task-quality/original/cases/livebook-pr-2800/ticket.md), [reference implementation](../../verification/task-quality/original/cases/livebook-pr-2800/reference.patch).

| Ticket requirement | Existing observation | Gap / proposed observation |
| --- | --- | --- |
| Incomplete, parser and tokenizer errors report original problem | Exact full strings for `X =`, `X ==/== a.`, `$a$` | Assert error type/reason and absence of exception-formatting failure without freezing decorative spacing |
| Correct source and location | Exact snippets and locations, all on line 1 | Add leading newline and indented line-2 variants for all three error forms, custom filename and error marker line |
| Ordinary runtime errors remain readable | Full string for `list_to_binary(1)` including an internal OTP source line | Assert bad argument, failing function and original argument, not the internal implementation line |
| The solution does more than suppress the crash | Existing partial probe drops snippets | Retain it; also mutate source extraction to always select the first line |

The existing equality assertions freeze box-drawing characters, all spacing, exact explanatory wording and `erl_eval.erl` line 900. The pinned runtime prevents ordinary version drift in a frozen release, but it does not turn that layout into a solver-visible requirement. A repair that preserves the same error type, source and correct location while indenting continuation lines differently is a credible false-negative candidate. The proposed positive alternative makes precisely that change only in Erlang exception formatting after applying the reference repair. It should pass the pristine prefix-based preservation tests and semantic checks but fail the existing full-string acceptance. This is a hypothesis to execute, not a reported outcome. [Current acceptance](../../verification/task-quality/original/cases/livebook-pr-2800/acceptance.patch), [pristine evaluator test](https://github.com/livebook-dev/livebook/blob/c374ac6a4b50d65b60d6112c5dd95bd79f7453dd/test/livebook/runtime/evaluator_test.exs), [historical formatter](https://github.com/livebook-dev/livebook/blob/c374ac6a4b50d65b60d6112c5dd95bd79f7453dd/lib/livebook/runtime/evaluator/formatter.ex).

[`replacement-acceptance.patch`](../../verification/task-quality/cases/livebook-pr-2800/replacement-acceptance.patch) retains the existing test identity and checks error class, reason, source and location plus absence of the formatting failure. The exception-class checks preserve a behavior the pristine test already enforces; they are not newly inferred from the reference patch. An evaluator that changes public exception classification would already fail original preservation. The seven supplemental cases cover the three original forms, three multiline forms and ordinary runtime error, inspecting error markers as well as text. [Existing original classification checks](https://github.com/livebook-dev/livebook/blob/c374ac6a4b50d65b60d6112c5dd95bd79f7453dd/test/livebook/runtime/evaluator_test.exs), [error annotation/source extraction](https://github.com/livebook-dev/livebook/blob/c374ac6a4b50d65b60d6112c5dd95bd79f7453dd/lib/livebook/runtime/evaluator.ex).

If this replacement is adopted, preserve the exact upstream acceptance-test patch separately for source reconstruction and update the curated reference tests consistently. Changing a grading oracle must produce a new release identity and invalidate relevant prior qualification; it must not rewrite old results. [Admission/source reconstruction policy](../case-admission.md), [evaluation release policy](../evaluation.md).

## 2822 — failed evaluation context isolation

Executable audit inputs: [supplemental checks](../../verification/task-quality/cases/livebook-pr-2822/acceptance.patch), [mutation specifications](../../verification/task-quality/cases/livebook-pr-2822/audit.json).

This is the deepest stateful task among these six. Successful contexts contain bindings, aliases, requires, imported functions/macros, context modules and process dictionary state. The evaluator merges some fields but treats imports and the dictionary as snapshots. Resetting a failed evaluation to an entirely fresh context therefore erases earlier imports and dictionary values. The reference carries those snapshots forward while clearing the failed context's deltas. This is not a claim to roll back arbitrary side effects such as files, ETS or spawned processes; the benchmark should remain explicit about which state it promises. [Ticket](../../verification/task-quality/original/cases/livebook-pr-2822/ticket.md), [reference repair](../../verification/task-quality/original/cases/livebook-pr-2822/reference.patch), [historical context merge/prune logic](https://github.com/livebook-dev/livebook/blob/5ee9a502af29daa8b499a5e0aba7c36f169968e6/lib/livebook/runtime/evaluator.ex).

| Ticket requirement | Existing observation | Gap / proposed observation |
| --- | --- | --- |
| Preserve prior imported functions and macros | Asserts at least two entries in the Integer function/macro lists | Compare exact prior import snapshots; call imported functions and macros in a later request |
| Preserve prior dictionary and reject failed writes/deletes | Exact dictionary equality after failed and merged contexts | Also introduce a new key in failed cell and read prior/deleted/new keys from a later evaluation |
| Do not leak new bindings, aliases or requires | Explicit empty/unchanged context assertions | Retain; assert later merged execution sees original binding and original alias |
| Do not leak failed modules | Asserts empty `context_modules` list | Also assert the failed module is not loadable; the implementation actually deletes failed definitions |
| Merging successful contexts with an error preserves guarantees | Inspects merged context fields | Execute a later cell with both errored and successful parent refs |
| The example failing assertion does not erase later assertions | No direct subsequent assertion sequence in new test | Import ExUnit assertions, fail an assertion, then successfully evaluate another assertion |

The new upstream test is strong in breadth but weak at the exact import boundary: `[_, _ | _]` proves a minimum count, not retention of the original functions/macros. The `restore-all-integer-imports` mutation widens Integer imports and can satisfy those length assertions; the supplemental test compares the exact prior snapshots and executes representative imports. The `retain-failed-process-dictionary` mutation tests a distinct wrong fix from the existing “erase dictionary” probe: keeping the failed cell's mutations rather than the pre-failure snapshot. [Current acceptance](../../verification/task-quality/original/cases/livebook-pr-2822/acceptance.patch), [current incomplete probe](../../verification/task-quality/original/cases/livebook-pr-2822/case.json).

The supplemental test explicitly checks that the failing evaluation returns an error containing its intended reason. This avoids treating a setup/compiler failure before the deliberate mutation sequence as evidence of rollback. The current helper was deliberately loosened from a terminal-result pattern to any output so the error test can use it; existing tests mostly inspect identifier metadata, but this change makes a direct intended-error assertion particularly valuable. [Acceptance helper change](../../verification/task-quality/original/cases/livebook-pr-2822/acceptance.patch).

Testing `Code.ensure_loaded?` checks a real module-side effect already handled in the evaluator error path. It does not require a specific private context representation beyond the public/context APIs the existing suite already uses. A future alternative design could be graded mainly through subsequent execution, but the current internal field assertions must then be reviewed together rather than silently retaining representation constraints. [Failed module cleanup](https://github.com/livebook-dev/livebook/blob/5ee9a502af29daa8b499a5e0aba7c36f169968e6/lib/livebook/runtime/evaluator.ex).

## 3076 — S3 workspace form ownership

Executable audit inputs: [supplemental checks](../../verification/task-quality/cases/livebook-pr-3076/acceptance.patch), [mutation specifications](../../verification/task-quality/cases/livebook-pr-3076/audit.json).

This is a valuable example of a small repair with meaningful integration reasoning. The old test submitted a dumped server struct containing `hub_id`; a browser submits only the displayed connection fields. That extra test-only value masked the component's use of a hub struct where an ID was needed. The curated acceptance removes the extra server-owned fields, then checks the created/updated struct, navigation, visible list and persisted state. One-line size does not make this an invalid task; the debugging boundary is the important part. [Ticket](../../verification/task-quality/original/cases/livebook-pr-3076/ticket.md), [reference patch](../../verification/task-quality/original/cases/livebook-pr-3076/reference.patch), [curated acceptance](../../verification/task-quality/original/cases/livebook-pr-3076/acceptance.patch), [historical form fields and handlers](https://github.com/livebook-dev/livebook/blob/bdb2b95a1d7fe837cd71e17688791d4785bb37e9/lib/livebook_web/live/hub/file_system_form_component.ex).

| Ticket requirement | Existing observation | Gap / proposed observation |
| --- | --- | --- |
| User submits only fields on the form | `Map.take` of bucket URL, region, access key and secret key | Adequately aligned with rendered fields; retain |
| Successful connection saves storage to the workspace | Local Bypass request, exact created struct and persisted membership | Adequate for personal workspace; exact struct includes ownership |
| Storage appears in the list | Asserts list HTML contains bucket URL | Retain |
| Existing editing works | Existing S3 edit test changes access key, checks broadcast and persistence | Retain |
| Validation still works | No invalid-form or rejected-S3-response tests in the targeted file | Add missing secret-key validation and a 403 connection rejection with no persistence |

The main gap is literal: the ticket explicitly promises continued validation, but all S3 cases in the selected test file are successful create/update/detach flows. The proposed invalid-field test leaves one credential blank and requires a disabled form plus a field error and absence of storage. The connection test uses a local 403 S3 response, requires a visible connection error, keeps the form open and checks no storage was persisted. The `ignore-s3-connectivity-failure` mutation still performs the request but discards its failure, so it specifically exercises the missing decision rather than merely causing an unmet mock expectation. `skip-secret-field-validation` removes one required displayed field. [Targeted historical suite](https://github.com/livebook-dev/livebook/blob/bdb2b95a1d7fe837cd71e17688791d4785bb37e9/test/livebook_web/live/hub/edit_live_test.exs), [S3 changeset](https://github.com/livebook-dev/livebook/blob/bdb2b95a1d7fe837cd71e17688791d4785bb37e9/lib/livebook/file_system/s3.ex), [connectivity/save flow](https://github.com/livebook-dev/livebook/blob/bdb2b95a1d7fe837cd71e17688791d4785bb37e9/lib/livebook_web/live/hub/file_system_form_component.ex).

The exact upstream patch also changes Teams tests and Git-storage tests. The curated task explicitly says personal workspace and S3; the manifest permits `teams_integration` and `git` exclusions. Do not describe a pass as proof of Teams or Git-storage behavior. Keeping those tests separate for provenance is appropriate, and adding cloud/service dependencies solely to reproduce the entire upstream PR is unnecessary for this declared task. [Upstream tests](../../verification/task-quality/original/cases/livebook-pr-3076/upstream-tests.patch), [manifest](../../verification/task-quality/original/cases/livebook-pr-3076/case.json), [ticket](../../verification/task-quality/original/cases/livebook-pr-3076/ticket.md).

## Execution needed before admission claims

For each case, execute the unchanged tree, reference repair, existing partial probe and integrity probe under the actual grader. Then execute the supplemental reference tests and each new mutation, recording the failing named assertion and distinguishing a task failure from an invalid test/setup failure. For 2800, execute the positive formatting alternative under both current and semantic acceptance to establish whether the predicted false negative is real. For 2663, execute the harmless-extra-indentation alternative and require it to preserve the semantic contract rather than treating any reference difference as a defect. Repeat the final reference checks after any test fixes, using bounded concurrency. The proposal metadata deliberately identifies each mutation's rationale so a rejected mutant is interpretable evidence rather than a mutation-score number. [Evaluation qualification rules](../evaluation.md), [case admission rules](../case-admission.md).

A case is ready when the final executable contract reflects the ticket, the reference passes it, realistic incomplete fixes fail for the intended behavioral reason, and acceptable alternatives are not rejected by accidental implementation detail. Passing these checks establishes evidence for these six declared contracts, not a general proof that any twelve historical PRs measure all software engineering ability. The twelve-case release should report its narrow distribution and public historical exposure alongside scores. [Public historical case policy](../adr/0002-historical-upstream-repairs.md), [public cases policy](../adr/0001-public-cases-and-solutions.md), [evaluation limitations](../evaluation.md).
