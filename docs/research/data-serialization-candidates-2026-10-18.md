# Data, serialization, and transformation candidates — 2026-10-18

This source-only research adds four candidate families in four projects not covered by the earlier rounds: Floki, Explorer, Nx, and Jason. NimbleCSV was also investigated and is retained as a conditional reserve. The objective is different observable work—tree queries, relational data, numerical tracing, macro evaluation, and streaming input—not a larger list of similar framework repairs.

The [selection guidelines](../pr-selection-guidelines.md), [admission contract](../case-admission.md), existing research reports, and [rejection register](../../cases_rejected/README.md) were screened first. Nothing here readmits the rejected Plausible cases or changes the inventory. No project builds, tests, model attempts, timing measurements, or performance comparisons ran. Proposed checks and incomplete controls remain unqualified.

## 1. Floki: make parsed `:has` selectors affect matching

**Source and provenance.** [Issue #482](https://github.com/philss/floki/issues/482) asks to find elements containing matching descendants, then continue selecting within the matched elements. [#623](https://github.com/philss/floki/pull/623), authored by `philss`, adds parsing; [#624](https://github.com/philss/floki/pull/624), authored by `bvobart`, adds matching. The author corrected an OR-versus-AND misunderstanding during review, before merge. The accepted tests distinguish comma alternatives from chained `:has` clauses. This correction is already in the accepted reference, not an additional PR to extract.

**Coordinated scope.** The full pair changes lexer rules, selector parsing, selector dispatch, and pseudo-class matching. Two test files cover parsing and public `Floki.find/2`; the README includes substantial formatting in addition to new documentation. #624 alone starts with the parser already present and changes two substantive matcher files; its parser edit only improves a diagnostic. Both are legitimate task shapes, but count them differently. [#623 complete diff](https://github.com/philss/floki/pull/623/files), [#624 complete diff](https://github.com/philss/floki/pull/624/files).

**Draft brief for #624 alone:**

> `:has(...)` is parsed but does not select the containing elements. Make it match elements with a matching descendant using the existing supported inner selectors. Comma-separated alternatives are OR; repeated `:has` clauses are AND. Preserve ordinary selectors and combinators outside `:has`.

For the full feature pair, replace the first sentence with a request to add that capability. State the supported inner syntax explicitly after contract review. This is a scoped Floki feature, not a promise of full CSS `:has` support. Upstream explicitly excludes combinators inside the argument and nested selector-taking pseudo-classes. Its README says “child” while the actual algorithm and nested-table tests traverse descendants, so the brief should say **descendant**. A schema or parser-struct equality test is not a substitute for correct public matching.

**Functional checks.** Use small parsed trees and the public query boundary: an immediate descendant; a grandchild; matching text/comment nodes versus actual elements; no match; `:has(*)`; comma OR; chained AND where the two witnesses are different descendants; an outer sibling/child combinator; stable document order and no duplicate result for multiple witnesses. Preserve plain tag/class/attribute matching and existing `:not` behavior. The upstream tests already cover many positive examples and nested tables. A plausible incomplete control handles only immediate children; another uses AND for comma alternatives. Both should compile and fail a named matching assertion, not a setup check.

**Reference challenge.** The shared parser immediately appends a selector after consuming an attribute and resumes parsing a fresh inner selector. By static inspection, an argument such as `[data-x].marked` risks becoming two alternatives instead of one conjunction; `img[src='x'].marked` has the same concern. This was not executed. Challenge it before promoting a broad compound-selector brief. Either establish/correct the intended complete contract, or keep #624 honestly scoped to the already parsed subset and record this pre-existing parser limitation. Do not claim the pair is a fully corrected CSS implementation, and do not quietly omit valid compound selectors from a broader promise. [Accepted parser](https://github.com/philss/floki/blob/f900ea1e5ac60e7f39980750a60c891b604fb67d/lib/floki/selector/parser.ex).

**Historical environment.** The pre-parser [Mix project](https://github.com/philss/floki/blob/be2b265c418cd704f043fdc17e4e404935e32557/mix.exs) requires Elixir `~> 1.14`, compiles the lexer with `:leex`, and includes an Erlang Mochiweb parser. [CI](https://github.com/philss/floki/blob/be2b265c418cd704f043fdc17e4e404935e32557/.github/workflows/ci.yml) exercises 1.18/OTP 27.2 and 1.14/OTP 24.2, with Mochiweb, FastHtml, and Html5ever variants. Pin the [lockfile](https://github.com/philss/floki/blob/be2b265c418cd704f043fdc17e4e404935e32557/mix.lock). Mochiweb is a meaningful service-free target for this selector feature; tests use both tuple trees and Floki's tree representation. Optional parser dependencies still appear in the project's dev/test dependency list, so their native preparation cannot be assumed absent merely because Mochiweb is selected. The [test helper](https://github.com/philss/floki/blob/be2b265c418cd704f043fdc17e4e404935e32557/test/test_helper.exs) configures parser-specific include/exclude tags and starts FastHtml only when selected. **Draft clarified brief:**

> Add `nulls_equal: true` to DataFrame joins so missing key values can match. Keep null keys nonmatching by default. Apply the option consistently to eager and lazy joins, including right joins, while preserving unmatched rows, column names, and ordinary non-null matches.

The public option name is part of the requested interface. The internal options-map representation is not a grading requirement. **Functional checks.** Use in-memory tables with unique row labels and compare row multisets unless the existing API promises order. The added upstream right-join tests assert only row count and the preserved right payload. Those assertions can pass even if the left null-key payload never joins. Add a specific assertion on that matched left payload, otherwise a plausible incomplete reference that forwards the option in the ordinary branch but hardcodes false in the right-join branch survives. That partial implementation is an excellent candidate control once compiled and executed. The PR description says all join types are tested, but the actual new tests cover default/inner/right; the report relies on the diff rather than that broader claim. ## 5. NimbleCSV: promising streaming reserve, with an encoding challenge

[Issue #57](https://github.com/dashbitco/nimble_csv/issues/57) and [#59](https://github.com/dashbitco/nimble_csv/pull/59), authored by `LostKobrakai`, introduce `to_line_stream/1` for arbitrarily chunked input. The single-parent pair is `31ab262d7b64a611249b3fe0d26d4c40878d30cc` → `f4b2a112c8a66c4c82ee206e814ff93927303f27`. One substantive implementation file coordinates generated parser configuration, newline scanning, buffered tails, and streaming CSV consumption; Mix/CI changes raise the minimum from Elixir 1.3 to 1.5 for `Stream.chunk_while`. The complete diff contains one test file, not several implementation modules. [Accepted diff](https://github.com/dashbitco/nimble_csv/pull/59/files).

A candidate brief would request lazy conversion of arbitrary chunks to newline-preserving lines, final unterminated-tail emission, and composition with `parse_stream`. Meaningful checks include empty chunks, multiple lines per chunk, CRLF split across chunks, quoted multiline CSV fields, finite-prefix consumption of an instrumented stream, and preservation of ordinary line streams. A plausible incomplete control drops the final unterminated tail. Laziness is a count/order property; never grade speed or memory usage.

**Do not yet promote an unrestricted encoding promise.** The implementation scans encoded newline bytes without tracking code-unit alignment. UTF-16LE input containing U+0A00 followed by U+0000 has bytes `00 0A 00 00`; `0A 00` resembles an encoded LF at an odd offset. Static inspection therefore gives a concrete possible spurious-line-split witness. The added UTF-16 test splits only on character boundaries and uses ordinary ASCII content, so it does not resolve this concern. This is an unexecuted reference challenge, not a claimed reproduced failure. A UTF-8-only task could be legitimate if openly scoped and independently reviewed; silently ignoring configured encodings would be unfair.

Historical [Mix](https://github.com/dashbitco/nimble_csv/blob/31ab262d7b64a611249b3fe0d26d4c40878d30cc/mix.exs) has no test/runtime dependencies, only ExDoc for docs; the inspected tree has no lockfile. [CI](https://github.com/dashbitco/nimble_csv/blob/31ab262d7b64a611249b3fe0d26d4c40878d30cc/.github/workflows/ci.yml) includes Elixir 1.10.4/OTP 23.0.3. [Test helper](https://github.com/dashbitco/nimble_csv/blob/31ab262d7b64a611249b3fe0d26d4c40878d30cc/test/test_helper.exs) only starts ExUnit. [README licensing](https://github.com/dashbitco/nimble_csv/blob/31ab262d7b64a611249b3fe0d26d4c40878d30cc/README.md#license) supplies Apache-2.0 and Plataformatec/Dashbit copyright notices; there is no root LICENSE file in the inspected tree. Later inspected source history contains no identified `to_line_stream` correction.
