## Requirements-first record

This section was written after reading the original issue/PR description and starting source/tests, before opening the accepted implementation diff or any new acceptance checks. The previously requested [candidate research note](translation-application-candidates-2026-10-18.md) already described the reference's approach; this review is independent of hidden checks, not wholly blind to reference commentary. No fixture or model result has been inspected.

The [original issue #171](https://github.com/mirego/accent/issues/171) asks for clients to download a compatible translation version without repeatedly replacing an exact tag in separately deployed systems. The [PR description](https://github.com/mirego/accent/pull/183) chooses Elixir version requirements as the fallback when a literal match is absent, and explicitly illustrates a stored `v1.1.4` selected by `>= 1.0.0` or `~> 1.1`. The issue's partial-tag example does not by itself authorize a wildcard syntax that the clarified brief does not promise.

**Proposed minimal solver brief:** “Allow file export and sync/merge requests to select a project's translation version with a semantic version requirement such as `~> 1.1`. Prefer an exact literal tag when present; otherwise select the highest compatible version in that project, accepting stored tags with a leading `v` and ignoring non-version tags. Preserve the existing outcomes for unmatched requests and requests without a version.” This is a clarified feature brief: it states product outcomes without naming the query helper, affected files, or required implementation shape.

Required semantics and preservation derived before assertion review:

1. Literal lookup has priority within the requested project, including arbitrary named tags and a literal tag whose text is itself a valid requirement. The existing [schema](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/lib/accent/schemas/version.ex) accepts non-semantic tags and enforces tag uniqueness per project; adding semantic fallback must not invalidate those existing tags.
2. With no literal match, select the highest semantic version satisfying the requested requirement from that project's versions. Numeric semantic ordering, rather than lexical text or insertion order, determines the maximum. A higher compatible version or matching literal in another project must not affect selection.
3. Valid stored versions with a lowercase leading `v` participate in fallback. Non-version tags are ignored during semantic candidate selection, but remain available through literal lookup. Do not silently broaden this to an unspecified normalization policy for uppercase prefixes, whitespace, multiple prefixes or incomplete stored versions.
4. Exercise the actual routed requests: `GET /export`, `POST /sync`, and `POST /merge` (the same merge controller also serves `/add-translations`). The [router](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/lib/web/router.ex), not outdated GET labels in the controller documentation, defines the methods. Export must return the selected version's file contents; successful sync/merge must persist translations and operations associated with the selected version. Inspect unrelated versions and projects to reject broad updates or dropped valid data.
5. For an unknown nonnil version, retain export's 404 and movement parsing's 422 rejection rather than choosing an unrelated or unversioned fallback. Omission retains ordinary unversioned export/sync/merge behavior. These differ from passing an explicit null value, which is not a required new policy. The [export controller](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/lib/web/controllers/export_controller.ex), [existing export tests](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/test/web/controllers/export_controller_test.exs), and [movement parser](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/lib/web/plugs/movement_context_parser.ex) establish those paths. A syntactically invalid requirement with no literal match is likewise unmatched, not a server crash.
6. Preserve existing request authentication/authorization and normal document/language/translation handling. Use ordinary local bearer credentials for movement requests through the endpoint, as in the [starting sync tests](https://github.com/mirego/accent/blob/9cdd5626da8cb71e4ef2ab45afc8b73632470cfe/test/web/controllers/sync_controller_test.exs). Do not strengthen export authorization as a hidden feature: its starting controller loads the project and the existing export tests use no bearer header.

Exact response prose, helper names, number of database queries, prerelease inclusion policy beyond the historical standard library, and selection among semantically equal tags are not new requirements. Equal-precedence tie fixtures need either accepting any compatible maximum or a visible policy. No performance claim or measurement is authorized.

## Accepted reference and follow-up challenge

The [accepted commit](https://github.com/mirego/accent/commit/e11088f6ec0b58fdb8dc0d0948ba167ed5388dc2) has the single parent `9cdd5626da8cb71e4ef2ab45afc8b73632470cfe`. Its three implementation paths add parsing of stored tags, exact-first semantic fallback, and project scoping before the movement lookup. Its fourth path is the upstream version-scope test file. The only fetched [inline review comment](https://github.com/mirego/accent/pull/183#discussion_r421513006) concerns pipe style, not an additional product requirement.

The [fixed scope](https://github.com/mirego/accent/blob/e11088f6ec0b58fdb8dc0d0948ba167ed5388dc2/lib/accent/scopes/version.ex) first checks for an exact match in the supplied query. Only its absence permits requirement parsing and candidate selection; malformed candidate tags are rejected before `Version.compare/2`. It sorts candidates by semantic precedence and selects the highest compatible tag. A valid but unsatisfied requirement and an invalid requirement both retain an empty literal-filter result, allowing existing endpoint rejection behavior. The nil clause is unchanged. Selection returns a query retaining its original project restriction, and the schema's per-project unique-tag index prevents duplicate selected rows within that scope.

The [movement-parser reorder](https://github.com/mirego/accent/blob/e11088f6ec0b58fdb8dc0d0948ba167ed5388dc2/lib/web/plugs/movement_context_parser.ex) is material because the lookup now executes a database read before returning its filter. Without it, another project's higher compatible version—or exact requirement-looking tag—could determine the intermediate filter and make a valid local request fail. The starting export, JIPT-export and GitHub-hook consumers already scope before lookup. No other unscoped application consumer was found in the starting tree. This supports the reference's project isolation statically; endpoint qualification must still demonstrate it.

Reference limits and possible overconstraint:

- The fixed [stored-tag parser](https://github.com/mirego/accent/blob/e11088f6ec0b58fdb8dc0d0948ba167ed5388dc2/lib/accent/schemas/version.ex) uses `String.trim_leading("v")`. Historical [String documentation](https://hexdocs.pm/elixir/1.9.4/String.html#trim_leading/2) specifies removal of all matching leading characters, so a tag such as `vv1.2.3` is accepted by this reference after normalization. Requiring rejection of repeated prefixes would therefore reveal a reference mismatch. The brief establishes ordinary lowercase `v` support but no exact prefix-count policy; do not silently score one. If curation intends strict single-prefix semantics, clarify the brief and replace/defer this reference rather than hiding the discrepancy.
- Historical [Version semantics](https://hexdocs.pm/elixir/1.9.4/Version.html) permit prereleases by default in `match?/3`, unlike Hex's default caller policy; build metadata does not affect precedence. Stored `1.2.3`, `v1.2.3` and build variants can therefore tie. The reference does not promise a stable tie winner. Avoid stable-only expectations or a particular tied row without an explicit visible contract.
- The upstream tests cover literal priority, requirement-looking literals, prefixed stored versions, the maximum compatible version, invalid tags and no match. They do not establish project-isolated export or persisted sync/merge results. Helper success cannot replace those application witnesses. [Exact upstream tests](https://github.com/mirego/accent/blob/e11088f6ec0b58fdb8dc0d0948ba167ed5388dc2/test/scopes/version_test.exs).
- A later [CLI version-support commit, #325](https://github.com/mirego/accent/commit/4efe980129caf6ab1eca6ccc7cec8cc5ee951c83) changes unmatched movement requests from 422 to 404 and alters their message. That later policy must not be imposed on this historical task. In [2026's VersionFinder extraction](https://github.com/mirego/accent/blob/0cbdcd07aa3958c2f080be2513bc5ab008d5906d/lib/accent/versions/version_finder.ex), exact-first, project-scoped, maximum-compatible selection remains, now returning a record directly. The associated tests retain the original semantic examples. The inspected path histories identify no focused correction that invalidates the bounded #183 behavior; this is a targeted source screen, not a proof about every later defect.

**Reference assessment:** no material defect found for the stated literal/ordinary semantic-version/project/request contract. The repeated-prefix and tie observations above are explicit boundaries on that conclusion. No alternative must copy the virtual field, eager query helper, sort pipeline or three-file shape.
