# Livebook as the next large application

Source-only investigation, 2026-10-11. No application builds, tests, benchmarks, forks, or case integration were performed. The candidates below have verified upstream fixes and test changes; they are **not qualified benchmark cases**.

Livebook is a strong complement to Plausible: it is a substantial Phoenix/LiveView application whose notebook sessions combine shared state, code evaluation, process lifecycles, persistence and runtime communication. Its session design serializes operations through a session process and applies the resulting operations in client processes. That creates useful Elixir and OTP diagnosis work beyond reporting/database behavior. This is a recommendation from the source, not a measured comparison. [Repository](https://github.com/livebook-dev/livebook), [session state design](https://github.com/livebook-dev/livebook/blob/main/lib/livebook/session/data.ex).

## The sample app and another alternative

The Phoenix/LiveView sample app already used by this benchmark is [LiveBeats](https://github.com/fly-apps/live_beats), a music-sharing demo. Our settings and playlist pilot cases introduce defects at its historical 2023 revision; they are not historical upstream PR repairs. See the [existing fixture review](web-fixture-review.md). It remains useful for focused web cases, but Livebook would add more application breadth.

[Changelog.com](https://github.com/thechangelog/changelog.com) is another substantial application: the production publishing/podcast CMS, built with Phoenix and PostgreSQL. Its source includes subscriptions, memberships, authorization policies and Oban jobs. It is a promising later choice for database-backed business workflows, while Livebook is the stronger immediate match for LiveView and runtime-state work. This is an architectural recommendation; no Changelog historical repair or runtime has been qualified. [Project description](https://github.com/thechangelog/changelog.com/blob/39d017883d1c32fea77d5e5c96c21dadd2e0e89f/README.md), [dependencies](https://github.com/thechangelog/changelog.com/blob/39d017883d1c32fea77d5e5c96c21dadd2e0e89f/mix.exs), [application source](https://github.com/thechangelog/changelog.com/tree/39d017883d1c32fea77d5e5c96c21dadd2e0e89f/lib/changelog).

## Qualification considerations

- Use each historical parent and its locked dependencies, following the Plausible approach. The #3076 revision records Elixir 1.18.3 and OTP 27.3.3; this is an input to an environment recipe, not a verified build. [Historical versions](https://github.com/livebook-dev/livebook/blob/02f00794c202e6a0a83f2c3cc94ee617a9d2f80c/versions).
- Start with the evaluator test file for #2822 and personal-workspace LiveView tests for #3076. The historical helper defaults to an embedded runtime and excludes unavailable Teams, Fly and Kubernetes integration tests. Record exact exclusions and ensure target acceptance tests execute. Do not select the similarly named Teams test file as the only oracle for #3076. [#2822 test helper](https://github.com/livebook-dev/livebook/blob/8dfe52258f3e383fe74a8fc1f2d0be38f0c9bbb6/test/test_helper.exs), [#3076 test helper](https://github.com/livebook-dev/livebook/blob/02f00794c202e6a0a83f2c3cc94ee617a9d2f80c/test/test_helper.exs).
- The inspected LiveView test uses `Phoenix.LiveViewTest`; the historical endpoint test configuration has `server: false`. Bypass still needs local loopback HTTP. A network-isolated container with working loopback should support that design, but this remains to be tested. [Test source](https://github.com/livebook-dev/livebook/blob/02f00794c202e6a0a83f2c3cc94ee617a9d2f80c/test/livebook_web/live/hub/edit_live_test.exs), [test configuration](https://github.com/livebook-dev/livebook/blob/02f00794c202e6a0a83f2c3cc94ee617a9d2f80c/config/test.exs).
- Avoid assuming current `main` has the same setup: its helper initializes Pythonx and Python, and other tests depend on Git credentials or external runtimes. Those are concrete reasons to qualify selected historical revisions rather than immediately running the whole current suite offline. [Current test helper](https://github.com/livebook-dev/livebook/blob/main/test/test_helper.exs).
- Before admission, require broken-fails/fixed-passes, meaningful agent regression coverage, protected-test preservation, rejected incomplete repairs and rejected early exit, with no external network during grading. The #3076 production repair is tiny, so label it as a diagnosis/form-boundary case rather than claiming substantial implementation difficulty. Agent context feasibility remains unmeasured.

An additional lead is [PR #3161](https://github.com/livebook-dev/livebook/pull/3161), which fixes notebook synchronization and adds a consecutive-cell update test. It also fixes smart-cell identity in the same PR, so it needs a coherence/scope review before becoming one case. Prefer the two cleaner candidates above for initial qualification.
