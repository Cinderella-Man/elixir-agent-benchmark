# Task-quality audit of the twelve PR cases — 2026-10-14

Follow-through: the [eleven-case v3 promotion](task-quality-promotion-2026-10-14.md) applies these findings. This report and its original evidence retain the pre-promotion scope; fixture links point to the archived inputs.

## Decision

**Do not use the current twelve-case grader unchanged.** Retain eleven task ideas, using the verified grading repairs where this audit demonstrates gaps. Livebook 2663 has no demonstrated scoring defect and gains additional semantic checks. Hold Plausible 6300: its reference does not satisfy the current timezone contract. This is a recommendation for a small Elixir bug-fix pilot, not certification of broad coding-agent ability.

The audit distinguishes three questions: does the environment execute, does a correct implementation pass, and does an incorrect implementation fail? All twelve original fixtures had valid identity-matching control receipts, and all twelve reference acceptance suites passed a fresh run with a different test order. That did not prevent material oracle gaps. [Recorded evidence](task-quality-evidence-2026-10-14.json)

## What was verified

- Read every ticket, manifest, implementation patch and grading patch, plus exact historical implementation and test files. The [Plausible review](../research/plausible-case-audit.md) and [Livebook review](../research/livebook-case-audit.md) map requirements to checks. A separate [peer review](../research/custom-oracle-review.md) challenged the custom checks and mutations.
- Validated exact source/tree provenance, current prepared-image availability, and the original unchanged/reference/incomplete/early-exit qualification identities for every case. Those 48 logical control outcomes were reused from matching receipts, not claimed as newly rerun controls.
- Executed every original reference acceptance suite in a fresh offline workspace with ExUnit seed 101, comparing every test identity/state with the seed-0 control. All twelve matched. This is a bounded repeatability check, not an estimate of flakiness.
- Executed custom unchanged/reference checks, targeted wrong implementations and valid formatting alternatives against the stated requirements. Ordinary negative controls had to complete and fail in a test body; setup failures and compilation errors were not accepted as defect detection.
- Replayed the wrong implementations that survived original acceptance through the complete original grader, including submitted regression tests, hidden acceptance, preservation and the requirement that submitted tests fail on the starting source. This establishes actual scoring consequences rather than merely pointing out missing assertions.

Execution used a separate data directory and ownership labels, with at most two audit workers and the existing per-workspace CPU/memory/process limits. No model generations or speed measurements were run. The active controller and its score history were not changed. Raw output is retained at `.local/task-audit/audit-results/`; the portable summary records stage outcomes, named failures, exact runtime/fixture identities and raw-file hashes. The exporter checks those input identities, requires every claimed mutation to fail a behavioral check that passed on the custom reference, and independently requires original preservation for positive alternatives. ## The reference itself is wrong for Plausible 6300's present contract

The public ticket says that weekday matching follows the site's timezone and preserves the intended time-of-day range. For `US/Eastern`, with Today ending at `2023-03-13 18:30:00Z`, the corresponding prior-year Monday is **2022-03-14**, from `04:00:00Z` to `18:30:00Z`. The reference instead starts at **2022-03-15 04:00:00Z**, a Tuesday. The new assertion failed in the test body with those exact expected/observed dates. All original assertions still passed. [Ticket](../../verification/task-quality/original/cases/plausible-pr-6300/ticket.md), [executable challenge](../../verification/task-quality/cases/plausible-pr-6300/acceptance.patch), [evidence](task-quality-evidence-2026-10-14.json)

The cause is the combination of UTC shifting and local-date matching. Shifting midnight EDT on March 13, 2023 one year in UTC lands at 23:00 EST on March 12, 2022. The code computes a two-day local-date adjustment and applies it back to the UTC instant, overshooting the intended Monday. The independent source review checked that both expected endpoints are EDT and that the calendar expectation matches the other-period convention. [Reference patch](../../verification/task-quality/original/cases/plausible-pr-6300/reference.patch), [peer review](../research/custom-oracle-review.md)

Do not “fix” the benchmark by changing the expected result to Tuesday. Choose either a clearly disclosed restriction to the historical fix's supported date/offset conditions, with corresponding ticket/check changes, or a different reference/task. Extending the implementation to cover DST would require explicitly documenting the curator-authored addition rather than pretending it is the accepted upstream PR. Until that decision is made, exclude this case from trusted comparative scores.

The separate hardcoded-one-day control fails the named leap-year and east-of-UTC checks. Its rejection is therefore independent of the DST failure of the reference; the audit does not count an already-broken reference requirement as evidence that this mutant was distinguished.

## What the custom controls revealed

The custom matrix contains **41 executed variants**: twelve starting revisions, twelve references, fifteen targeted wrong implementations and two valid formatting alternatives. All twelve starting revisions failed behaviorally; eleven references passed; all fifteen wrong implementations failed a named behavioral check that passed on their reference; both valid alternatives passed the semantic checks and original preservation. The one unmet positive expectation is 6300's reference, investigated above. These outcomes are not 41 independent task samples.

**Fourteen targeted wrong implementations across eleven cases passed the complete original grader.** Each passed submitted regression tests, hidden acceptance, original preservation and the fail-before/pass-after regression-test requirement. Their submissions included the existing reference regression-test patch; the scoring gap is therefore not explained by omitting the benchmark's submitted-test obligation. The strengthened checks reject all fourteen for named requirements that pass on the reference.

The remaining wrong implementation, 2822's failed-dictionary retention, already failed an original acceptance identity and was not counted as a scoring false positive. No new wrong implementation was needed for 2663: its existing two-digit-cap qualification control already fails, and the custom work adds semantic boundary checks and the passing extra-space alternative. Thus the audit demonstrates fourteen accepted wrong submissions, not fourteen failing tasks or a false-positive rate.

The important patterns are concrete:

- **Cache tests must not repair the product before observing it.** Plausible 5956's original test calls a refresh helper before every request. A no-op configuration-write cache update passes those acceptance checks; the direct creation request receives 404 in the new test. The new path also exercises repeated settings changes and another site's script, and parses returned JavaScript without executing it. It retains the starting repository's serializer conventions; it is not a browser-ingestion end-to-end test.
- **Authorization needs scope as well as role.** An Editor of a different team must not gain access to the target site's domain-change form. Viewer and outsider examples alone do not distinguish that mistake. Shared-link checks additionally cover malformed edits with an existing association and the parent settings page's permission boundary.
- **Preservation needs positive witnesses.** Disabling all imported special-event data, discarding ordinary imported page goals, or dropping valid aggregate legacy time-on-page can avoid the reported crash while violating the ticket. The added fixtures establish both exclusion of unsupported data and retention of supported data. Time-on-page here is a business metric derived from fixed synthetic event timestamps, not an execution-time measurement.
- **UI tests must use the actual data shape and workflow.** Livebook 2219's original new test exercises only numeric replacement, while the ticket promises text input. New tests cover text editing, append, nested frames and sibling output. Livebook 3076 now checks missing credentials and a local S3 403 response as well as the existing successful form path.
- **State inspection needs exact content and subsequent behavior.** Livebook 2822's “at least two imports” assertion accepts an incorrectly widened import set. The new check compares import membership without imposing list order, then executes imported functions/macros and checks dictionary state after errors and context merging. It also checks that failed-cell modules are not loadable.
- **Formatting differences are not automatically defects.** An extra-space Markdown implementation passed original preservation, original acceptance and the AST/idempotence checks. An indented Erlang diagnostic passed original preservation and all semantic source/location checks, but failed the original exact-text acceptance. The latter is a demonstrated fairness problem, addressed by the supplied replacement overlay. A further exploratory 2663 candidate added a space to every multi-digit continuation; the pinned parser retained that space inside fenced code, and the semantic check correctly rejected it. That candidate is not a valid alternative or another fairness defect. Its separate result is included in the evidence export and is not counted in the 41-variant matrix.

These are deliberately targeted controls, not a random sample of wrong patches. Their survival/rejection counts must not be reported as a population false-positive rate or a model accuracy result. No real model was asked to produce these patches.

## Which tasks to select next

The [primary-source research](../research/task-quality-and-verification.md) supports keeping authentic repository work with clear, executable outcomes. A merge, a passing reference and one fail-before/pass-after test are necessary evidence in this workflow, but do not establish a good benchmark task.

For this project, favor a varied set of Elixir work: Phoenix/LiveView workflows, Ecto data and query invariants, OTP process ownership/restarts/cancellation, serialization and authorization boundaries, bounded feature additions, and explicit-interface refactors. The present twelve are all bug-fix tasks from two applications. They contain useful integration and state work, but do not yet represent feature development, broad OTP supervision work or refactoring.

Good tasks have enough information in the ticket and starting tree to derive every required outcome, observable positive and negative examples, relevant preservation checks, and a dependable offline environment. Good custom verification follows the real request/render/query/evaluation boundary. Prefer a few hand-written incomplete repairs tied to individual requirements over a generic mutation score. Where a check seems overly restrictive, try a behavior-preserving alternative as a positive control.

Defer tasks that depend on unavailable credentials or live services, subjective quality judgments, unstated symbols or exact formatting, infrastructure failure masquerading as the bug, or a speed objective that the functional oracle cannot measure. For a feature, turn absence into a named assertion rather than an import/compiler crash. For a refactor, state the interface/structural objective and preserve behavior; patch similarity is not an objective.

For every case, map both directions: each assertion must be justified by the solver-visible contract, and each material requirement must have a discriminating check. The first catches unfair rejection; the second catches undeserved passes. Preserve authentic upstream source separately from curator-authored tests. A revised oracle must get a new frozen release identity.

## Limits and release implications

- **Eleven retained ideas remain a small pilot.** With the current twelve-case scoring rule, one case changes the score by 8⅓ percentage points. Cases share applications and implementation conventions; they are not independent random samples of software work. Report per-case outcomes and repeated runs under comparable settings before making strong model-ranking claims.
- **Public exposure remains possible.** PRs, fixes and grader source are public. Offline workspaces prevent live retrieval through the workspace, not pretraining exposure. Do not describe this historical corpus as uncontaminated.
- **Qualification binds this environment.** The audit reused verified source/preparation artifacts and recorded immutable application/service image identities. Some manifest image inputs still use tags. This work does not establish that an arbitrary future cold build will resolve identical packages or that every supported host behaves identically. Preserve/distribute the qualified runtime artifacts or qualify a newly built environment separately.
- **Coverage is finite.** These checks cover the stated cases and the enumerated failure modes. They do not prove every conceivable implementation correct, certify all application security, exercise enterprise/Git/cloud variants excluded by the original contracts, or demonstrate zero flakiness.
- **Reviews are agent reviews.** No independent human attestation or blind human implementation has been fabricated. The source reviews and separate peer review are recorded as what they are.

Before using the improved cases for scored comparisons, promote the chosen overlays into the case bundles, update commands and required test identities, preserve upstream test partitions, rerun complete unchanged/reference/incomplete/integrity qualification against those final inputs, and freeze a new release. Resolve 6300 first or leave it out. Existing model scores should retain their original release and must not be silently reinterpreted under the new checks.
